Validation and Measurement

If you can't measure your agent's quality, latency, and cost per run, you're running a demo in production.

Running example: the ops agent, months in. How do you know an improvement is real — not noise, or a gain for most users that quietly breaks it for one team?

The Evaluation Pyramid

A single accuracy number is necessary and almost useless on its own — it can't tell you which subsystem caused a regression.

If our ops agent's success rate drops from 84% to 76%, that could be retrieval, a tool schema, planning, context assembly, or a model change. One number can't distinguish among five hypotheses.

Cheapest layer first, most expensive last
flowchart TD A["Unit assertions on tools, schemas, parsers
- thousands of cases, microseconds each"] B["Component metrics: retrieval, tool selection, args
- hundreds of cases, milliseconds each"] C["Trajectory evaluation: valid and efficient path?
- hundreds of cases, seconds each"] D["Outcome evaluation: did it actually succeed?
- tens-hundreds of cases, plus judge"] E["Human review of a stratified sample
- tens of cases, expert minutes"] F["Production sampling and user feedback
- continuous"] A --> B --> C --> D --> E --> F
  • Cost per case rises and volume falls as you go up — cheap layers must catch most defects before expensive ones run.
  • A layered picture localizes a regression instead of just detecting one.
🎯 OpenAI Interview Pointer The book's framing — "if you can't measure quality, latency, and cost per run, you're running a demo in production" — is a strong opener for any evaluation-design question.

Component Metrics

Component metrics answer "which subsystem is failing?" — each one is cheap, deterministic where possible, and independently trackable over time.

Metric → what it localizes
MetricDefinitionLocalizes
Tool selection accuracyChosen tool matches labeled correct oneDescriptions, routing
Argument validityCalls passing schema validation first trySchema design, units
Retrieval recall@kRequired evidence present in top kIndex, chunking, query
Context precisionAssembled context actually relevantSelection policy, dilution
GroundednessClaims supported by retrieved evidenceSynthesis, verification

Termination correctnessRuns stop for the right reasonLoop bounds, stopping policy
Deep Dive: groundedness and correctness are different metrics
A claim can be fully supported by retrieved evidence and still be wrong — because the evidence itself was wrong or outdated. Groundedness measures faithfulness to sources; correctness measures agreement with reality. A system that only measures groundedness rewards an agent for confidently repeating a stale document.
🎯 OpenAI Interview Pointer Interviewers probe the groundedness-vs-correctness distinction specifically, per the book. Naming both — and the failure mode of optimizing only the first — shows real evals depth.

Trajectory Evaluation

An agent can reach a correct answer through a wasteful, unsafe, or lucky path — outcome-only evaluation can't see the difference, so it can't warn you before the luck runs out.

Compare to a path vs. assert properties of it
flowchart LR subgraph Naive["Compare to ONE reference path"] N1[Any deviation = failure] --> N2[Breaks on valid alternate strategies] end subgraph Working["Assert properties of the path"] W1["e.g. never calls issue_refund
before verifying order status"] --> W2[Several correct strategies pass] W2 --> W3[Lucky-but-unsafe paths still fail] end
  • Trajectory assertions encode policy executably — "must not call X before Y," "must stop within N steps of sufficient evidence."
  • Write safety assertions before success-case assertions. They encode policy, never go obsolete, and matter most at 3am during an incident.
🎯 OpenAI Interview Pointer The book: a candidate who starts evaluation from safety assertions, not accuracy, "reads as someone who has operated a system with consequences." A precise, quotable framing worth having ready.

Designing a Judge Rubric

For open-ended output there's no reference string to match, so a model judge is often the only scalable option — but it's an unvalidated classifier, and treating it as ground truth without validation is the most common measurement error in this field.

Three properties of a usable rubric
flowchart TD A["Decompose into independent criteria
(groundedness, completeness, correctness, format -
never one blended 'quality' score)"] --> B B["Anchor every level with a concrete example
('3 = every claim cited', NOT '3 = good')"] --> C C["Require evidence before the score
(quote the span that supports/contradicts each claim)"]
  • A single blended "quality" score correlates with length and fluency — not what you think it's measuring.
  • The quotation requirement is what turns "vibes" into an actual check.

Validating the Judge

A judge only counts as a measurement instrument once it's calibrated against humans — and that calibration figure has to travel with every number it produces afterward.

The calibration gate
flowchart TD A["Human-labeled calibration set, n >= 100"] --> B["Compute Cohen's kappa
(corrects for chance agreement)"] B --> C{"kappa >= 0.60?"} C -->|no| X["Not usable alone -
report as unmeasured"] C -->|yes| D["Check position bias
(randomize order, compare)"] D --> E{"Bias <= 10 points?"} E -->|no| X E -->|yes| F["Usable - report kappa
alongside every score"]
  • Never judge with the model that generated the answer. Self-preference is measurable and real.
  • Randomize presentation order; report an inconsistent verdict as a tie, not a coin-flip win.
Deep Dive: the kappa formula, and why raw agreement isn't enough
Raw agreement overstates quality when one label dominates — a judge that always guesses the majority class looks great on raw agreement while adding zero information. Cohen's kappa fixes this: κ = (observed − expected) / (1 − expected), where expected agreement is what two random labelers would achieve by chance given the label distribution. The book's floor: κ below 0.60 means the judge isn't usable alone.
🎯 OpenAI Interview Pointer "Never judge with the model that generated the answer" plus kappa/position-bias mechanics is a concrete, mechanism-level answer — much stronger than "we use GPT-4 as a judge."

Golden Datasets and Sample Size Arithmetic

The dataset determines what your numbers mean — and most reported small improvements in this field are not actually measurable, given how small most eval suites are.

  • Stratify by segment (intent, tenant size, recency, difficulty) and report per stratum — aggregate accuracy hides segment collapse.
  • Include failure cases explicitly — refusal, escalation, "insufficient evidence" at a realistic proportion.
  • Version with a datasheet: collection window, filters, dedup method, split strategy, label source.
  • Refresh on a schedule, measure drift against production's actual distribution.
How much a small suite can actually detect
flowchart TD A["At baseline p=0.8, a 5-point gain
needs ~1,000 cases/arm"] B["A 2-point gain needs
~6,000 cases/arm"] C["A 200-case suite can't reliably detect
anything smaller than ~12 points"] A --> B --> C
Deep Dive: the actual arithmetic
To detect a difference δ in a success rate near p, sample size per arm is approximately n ≈ 15.7 × p(1−p) / δ². This is why a 200-case suite reporting a 3-point gain has, almost certainly, reported noise. Two legitimate responses: run paired evaluation (same cases, both variants, test the per-case difference — needs far fewer cases), or accept offline evaluation only gates large changes and detect small ones through production experiments where the traffic exists.
🎯 OpenAI Interview Pointer The book is blunt: saying "most reported agent improvements are not measurable" unprompted, backed by this arithmetic, is "quantitative, correct, and uncomfortable" — probably the single highest-leverage line in this chapter for an evals-focused panel.

The CI Release Gate

Every layer of the pyramid converges into one decision: does this change ship? The gate checks safety absolutely, quality against a significance test, and cost as a visible trade — never silently.

One evaluation run inside CI
sequenceDiagram participant PR as Pull Request participant H as Eval Harness participant A as Agent Under Test participant J as Judge participant G as Release Gate PR->>H: commit sha, config diff H->>A: run 640 cases, 8 strata, paired w/ baseline A-->>H: trajectories, tokens, cost H->>H: trajectory assertions first, deterministic H->>J: open-ended answers, both orders J-->>H: verdicts + quoted spans H->>G: paired significance test, PER STRATUM G-->>PR: block / allow, with the reason
  • Safety assertions gate absolutely — any failure blocks, no exceptions.
  • Quality gates per stratum with a significance test, not just on the mean.
  • Cost is reported, and a ceiling breach blocks — a quality gain that triples spend must be a visible decision.
Deep Dive: The Evaluation Suite That Blessed a Fifteen-Point Segment Collapse
A real case from the book. A document QA agent serving 11 enterprise tenants shipped a retrieval change that improved aggregate accuracy from 79% to 81%. Within two weeks, one tenant escalated — their segment had fallen from 82% to 67%. Why: the eval set was drawn proportionally to traffic, so that tenant was only ~4% of it; their corpus leaned on heavy internal abbreviations, and the change shifted weight toward dense retrieval — exactly the direction that hurts exact-token matching on abbreviations. The aggregate improvement was real, and the collapse was invisible inside it. Fix: stratified reporting with a per-stratum floor — no release may drop any stratum by more than 3 points regardless of the aggregate — plus per-tenant production monitoring with automatic alerting.
🎯 OpenAI Interview Pointer Close to a perfect answer to "why gate per-stratum instead of on the mean." The book's own line: "aggregate metrics are a summary, and summaries hide exactly the failures that generate escalations."
