Running example: our ops agent, months in production. It's slowly getting better — the question is where that improvement actually lives.

Four Learning Surfaces

An agentic system can improve in four places — context, memory, procedure, or parameters — and each is roughly ten times slower and costlier to iterate on than the one before it.

Work down this table, not up
SurfaceStoresIteration timeReversible?Cost
ContextInstructions, exemplars, evidenceMinutesInstantlyTokens/request
MemoryFacts, preferences, correctionsImmediateYes, supersessionStorage + retrieval
ProcedureValidated tool sequencesHoursYes, version pinEvaluation runs
ParametersModel weightsDays-weeksOnly by redeployTraining + serving
  • Most teams reaching for fine-tuning haven't fixed tool schemas, retrieval, or exemplar selection yet — fine-tuning will faithfully bake those defects into weights that take weeks to change.
  • "How would you improve an underperforming agent?" → walking down this table in order is the answer.

Dynamic Few-Shot Selection

A fixed set of examples in the system prompt is a compromise — chosen for the average request, optimal for none. Pulling examples that match THIS request instead measurably improves formatting and tool selection.

For our ops agent, "restart service X" and "roll back flag Y" shouldn't see the same three examples every time.

Select → rank → diversify → cache
flowchart TD R[Incoming request] --> Sim[Retrieve candidates by similarity] Sim --> Rank["Rank by RECORDED OUTCOME quality
(not just how similar)"] Rank --> Div["Enforce diversity, avoid
3 near-identical examples"] Div --> Cache["Cache one set per cluster,
where traffic repeats"]
  • Select on the input, score on the outcome — a similar exemplar that was itself a mediocre run just teaches mediocrity.
  • Exemplars sit above the user's turn — swapping them per request invalidates the prompt prefix cache (Ch. 6). Cache one set per cluster where traffic repeats.
Deep Dive: the actual scoring formula
Each candidate scores as λ × relevance − (1−λ) × redundancy_to_selected + 0.15 × outcome_score. The redundancy term is what stops three examples of the same shape from crowding out the one that actually matches this request's pattern.

Verbal Reinforcement at Runtime (Reflexion)

Reflexion turns a failure into a written lesson placed in context for the next attempt. Nothing about the model changes — this is a runtime mechanism, not training.

Only works with an external signal
flowchart TD A[Attempt fails] --> B{External signal? test,
validator, API rejection} B -->|no oracle| Stop["Don't add reflexion —
it amplifies confident errors"] B -->|yes| C["Write a SPECIFIC lesson,
not 'be more careful'"] C --> D[Inject into next attempt] D --> E{Bounded?} E -->|under cap| A E -->|hit cap| F[Escalate, stop reflecting]
  • Needs three things: an external failure signal, a lesson specific enough to change behavior, and a hard attempt cap.
  • Without an external oracle, the model grading its own attempt produces confidently wrong lessons that contaminate every later attempt.
🎯 OpenAI Interview Pointer "Explain Reflexion and how you'd implement it in a production coding agent" is a documented question in this book. The strong answer names all three requirements — not just "the agent reflects on its mistakes."

The Skill Library and Its Promotion Gate

A skill is a named, parameterized tool-call sequence with a precondition, postcondition, and measured success rate. The whole design problem is the gate between "a run succeeded once" and "this is now a trusted skill."

Nothing reaches production without both gates
flowchart TD A[Successful run traces] --> B[Extract candidate, generalize args] B --> C{Duplicate of
existing skill?} C -->|yes| D[Discard] C -->|no| E["Offline eval on HELD-OUT cases
(never its own source traces)"] E --> F{Success >= baseline + margin?} F -->|no| D F -->|yes| G[Shadow: small % of live traffic] G --> H{Live success >= baseline?} H -->|yes| I[Production skill library] H -->|no| D I --> J{Regresses later?} J -->|yes| K[Auto-demote, no human needed]
  • Evaluate only on held-out cases the skill never produced — grading on its own traces measures memorization.
  • Two gates in sequence: beat baseline offline by a margin, then survive a shadow period on real traffic.
  • Demotion is automatic — a skill encoding last quarter's API shape must leave production without a human noticing first.
Deep Dive: the actual gate numbers
Book's reference values: promotion margin = beat baseline by 5 points; shadow minimum = 200 live attempts before promotion; demotion floor = 4 points below baseline triggers automatic removal. A library that only grows becomes a liability within about two quarters — demotion is what keeps it honest.
🎯 OpenAI Interview Pointer This mechanism — offline gate, shadow deployment, automatic demotion — is an evaluation harness applied to a learning surface. Describing this gate precisely, not just "we test skills before using them," is high-leverage for an evals-focused panel.

When Parameter Updates Earn Their Cost

Fine-tuning gets proposed far more often than it's actually the right call — but it decisively is, in three specific situations.

Three situations where it wins
SituationWhy it wins here
Strict format/protocol at high volumeA small fine-tuned model matches a larger prompted one at a fraction of serving cost; every successful run is a free label
Domain vocabulary the base model lacksNo amount of prompting reliably overrides a strong prior on unusually-used words
A hard cost/latency ceiling, after cheaper surfaces are exhaustedDistillation onto a smaller model buys the ceiling back
  • Knowledge gaps are a retrieval problem, full stop — fine-tuning doesn't fix a model not knowing something.
  • What you give up: a fine-tuned model freezes the task definition. When the business definition changes, you retrain instead of editing a prompt — keep a prompted fallback for exactly this reason.

The Data Flywheel

Production traces are your most valuable training asset, and also the most dangerous one — the failure modes are subtle, and the resulting offline metrics look great while being meaningless.

Three safety gates
flowchart LR A["Production traces
+ outcomes/feedback"] --> G1["Gate 1: Deduplicate
by trajectory hash + embedding"] G1 --> G2["Gate 2: Split held-out by
TIME and USER, never random"] G2 --> G3["Gate 3: Human adjudication
on low-agreement cases"] G3 --> D["Candidate dataset + datasheet"]
  • Deduplicate first — 100,000 raw traces might be a few thousand distinct problems; without dedup the model overfits to the popular ones and the eval set contains their twins.
  • Split by time and user, never at random — a random split puts a user's near-identical requests on both sides, quietly inflating every number you'll report.
  • Route low-agreement, high-impact cases to humans — "the user didn't complain" isn't the same thing as "correct."
  • Ship a datasheet with every dataset — collection window, filters, dedup effect, split strategy, label source, known biases.
Deep Dive: The Fine-Tune That Scored 94% and Failed in Production
A real case from the book. A routing agent's fine-tune reported 94% accuracy held-out, beating an 81% prompted baseline — then hit only ~78% in production, below the baseline it replaced. Three compounding errors: (1) the held-out set was split at random from 140,000 traces that, after dedup, were only ~9,000 distinct requests — many "held-out" items had near-twins in training; (2) labels came from a previous version of the same system's routing decisions, so the model learned to reproduce old errors, scored as correct; (3) the corpus covered one quarter, missing categories that only appear at fiscal year-end. Fix: deduplicate to distinct problems, split by time (most recent 4 weeks held out entirely), relabel a stratified sample by human adjudication. The honest number came out near 83% — production matched it within two points.
🎯 OpenAI Interview Pointer Close to a perfect fit for an Agent-Evals-focused panel. The book's own advice: when an offline gain looks surprisingly large, suspect leakage first — saying that unprompted is described as a strong senior signal.

Cheat Sheet

Four learning surfaces
Context → memory → procedure → parameters. Exhaust cheap ones first — ~10x cost jump each rung
Dynamic few-shot selection
Select by similarity, rank by outcome, enforce diversity, watch the prefix cache
Reflexion
Runtime only — needs external oracle + specific lesson + bounded attempts, never self-graded
Skill promotion gate
Held-out offline eval → shadow traffic → production, auto-demote on regression
Fine-tuning
Earns its cost for format/protocol at volume, vocabulary, or a cost/latency ceiling — never knowledge gaps
Data flywheel
Dedup → split by time/user → human-adjudicate. Suspect leakage first when a gain looks too good
