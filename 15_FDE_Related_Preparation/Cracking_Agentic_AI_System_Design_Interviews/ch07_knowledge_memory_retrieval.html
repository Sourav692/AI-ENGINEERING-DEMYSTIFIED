Knowledge, Memory, and Retrieval

Memory is a write problem before it's a retrieval problem. The highest-leverage decisions are about what never gets stored in the first place.

Memory Is a Write Problem

The most valuable memory entries are conclusions with a source attached — "the billing contact is finance@acme.example, confirmed 3 March from ticket 88214" — not raw transcript fragments.

Six months of embedding every conversation turn gets you a store full of low-value fragments, retrieval that returns plausible-looking noise, and an agent that confidently recalls a preference the user retracted back in March.

Naive embedding vs. a write policy
flowchart LR A[Every conversation turn] -->|naive: embed everything| B[Millions of low-value fragments] A -->|write policy: extract conclusions| C[A few durable, sourced facts] B --> D[Retrieval returns plausible noise] C --> E[Retrieval returns the right answer]
  • Retrieval quality is bounded above by what you chose to store — you can't retrieve your way out of a bad write policy.
  • When asked "how would you design agent memory," leading with the write policy (not the vector index) is the differentiating move.

Deep Dive: why "what's the renewal date" breaks in a vector store
A fact with exactly one correct value, retrieved by similarity, comes back with several plausible alternatives and no way to choose. "This customer's tier" or "this contract's renewal date" needs exact lookup by key, not nearest-neighbor search. Teams that force semantic facts into a vector store discover this the hard way.
🎯 OpenAI Interview Pointer "Why not just put everything in a vector store?" is a near-guaranteed follow-up. The specific answer — similarity search can't distinguish "the one correct value" from "several plausible ones" — shows real understanding.

The Write Policy

Before any candidate memory gets written, it has to pass four gates.

Four gates before anything is written
flowchart TD F[Candidate fact] --> Q1{Durable? true
next month too} Q1 -->|no| X1[Drop] Q1 -->|yes| Q2{Reusable? would a
future run read it} Q2 -->|no| X2[Drop] Q2 -->|yes| Q3{Attributable? source,
timestamp, confidence} Q3 -->|no| X3[Drop] Q3 -->|yes| Q4{Permitted?
regulated category} Q4 -->|no| X4[Reject or redact] Q4 -->|yes| OK[Write as a typed fact]
  • Facts are extracted as typed (subject, predicate, value) records at write time — never stored as raw conversation turns.
  • Regulated categories (health, payment, government IDs) are enforced on the write path — the read path is too late.
  • A contradicting fact supersedes, not deletes — kept with a pointer, so the system can answer "why did it believe X in April?"
Deep Dive: the memory that remembered a retracted instruction for four months
A real case from the book. A user told a scheduling assistant in January to always book travel through a specific vendor. In February the firm switched vendors and the user said so — but through May, the assistant kept proposing the original vendor about one time in four. Why: both statements were separate episodic entries, and retrieval returned whichever was more similar to the query — the January phrasing just happened to rank higher. Nothing knew the two entries were about the same predicate. Fix: extract typed facts so contradictions collide by construction, supersede instead of coexisting, and add an eval suite that seeds contradictory histories and asserts the newer fact wins.

The Retrieval Contract

Every memory read must be bounded by tokens, scoped by tenant, and attributable to a source — those three properties keep memory from being a source of randomness.

One memory read cycle
sequenceDiagram participant A as Agent step participant M as Memory Service participant V as Vector index participant L as Lexical index participant F as Fact store A->>M: read(query, tenant, max_tokens) M->>V: ANN top-40, tenant filter M->>L: BM25 top-40, tenant filter V-->>M: candidates + scores L-->>M: candidates + scores M->>M: fuse by rank, drop superseded M->>F: hydrate facts by id F-->>M: facts with provenance M-->>A: Evidence[] under max_tokens
  • Tenancy is enforced inside the store (row-level security or separate indexes), not just an app-layer filter that can silently fail open.
  • Dense (embedding) and lexical (BM25) search get combined by rank, not raw score.
Deep Dive: fuse by rank, never by raw score
The obvious approach — 0.7 × cosine + 0.3 × BM25 — breaks three ways: cosine and BM25 sit on incomparable scales, so weights are arbitrary; BM25 drifts as the corpus grows, silently reweighting over time; and normalizing needs each score's distribution, which changes whenever either index is retuned. Reciprocal rank fusion fixes this: score each doc as Σ 1/(k + rank) across result lists (k = 60 standard). Only ordinal position matters, so it's scale-free and stable across reindexing. Same principle applies to combining a judge's rating with a heuristic metric, or fusing reranker outputs.
🎯 OpenAI Interview Pointer A real interview drill in the book: "explain why fuse by rank rather than score, and where else this applies." Naming the general principle — ordinal beats cardinal combination when scales are incomparable — is what separates a strong answer from just reciting the RRF formula.

Consolidation, Decay, and Forgetting

Facts should fade on a schedule, not accumulate forever — otherwise "eviction volume" becomes the only warning sign that your write policy is admitting the wrong things.

  • Each fact scores on salience, decaying with age (a configurable half-life, e.g. 90 days) unless it keeps getting retrieved and used.
  • Consolidation runs offline, not on the request path — a background job clusters episodic facts and distills stable semantic traits.
  • Decay happens per predicate, not globally — a customer's tier barely ages; this week's on-call engineer ages fast.

Multi-Tenancy, Erasure, and Audit

A regulated buyer will audit three things: that one tenant's memory can never leak to another, that deletion is actually complete, and that every answer can point to its source.

  • Isolation: enforced in the store — an app-level filter fails open under an untested code path, and that failure is a cross-tenant leak.
  • Erasure: must remove the fact, its vector, its lexical posting, and every cached summary derived from it. Design the fan-out from day one.
  • Explainability: every answer must show which memory entries contributed — falls straight out of storing provenance in the schema.

Hierarchical Memory Compaction and Lifecycle GC

At millions of episodic observations, raw vector search breaks down — index bloat, semantic collisions, contradictory recall. The fix is a three-tier lifecycle that consolidates as data ages.

Working → nearline episodic → offline semantic
flowchart LR A["Working memory
(ephemeral, discarded at session end)"] --> B["Nearline episodic
(vector + fact log, recency decay)"] B --> C["Offline semantic profile
(batch-distilled, consolidated traits)"]
  • A background batch job inspects hundreds of episodic facts, clusters by subject/predicate, resolves contradictions, writes compact traits.
Deep Dive: GDPR Article 17 — hard erasure, not soft deletion
A "right to be forgotten" request isn't satisfied by soft-deletion. A compliant erasure is a coordinated purge: hard-delete matching rows in the relational store → delete corresponding vectors → remove subject references from BM25 postings → invalidate and regenerate any cached summaries derived from the erased facts. Miss one tier and a "deleted" fact is still recoverable somewhere.

Bitemporal Memory: Valid-Time vs. System-Time

A fact's real-world validity and the moment it was recorded are two different timelines — mixing them up means an agent answers "who's the lead architect now" when asked "who was it in Q3 2024."

Filtering on the query's target time
flowchart TD Q["Query: who was architect in Q3 2024?"] --> Check{as_of time falls within
this fact's valid interval?} Check -->|yes| Match[Return this historical fact] Check -->|no| Skip["Skip, even if most similar"]
  • Valid-time: the real-world interval a fact was actually true.
  • System-time: the timestamp the database recorded the assertion.
  • A retrieval filter enforces both — target time inside the valid interval, and the system must have known by then — eliminating anachronisms by construction.
🎯 OpenAI Interview Pointer A sharper version of "handle time-sensitive facts" than most candidates offer. Naming valid-time vs. system-time explicitly — not just "we'd add a timestamp" — signals you've hit this class of bug before.
