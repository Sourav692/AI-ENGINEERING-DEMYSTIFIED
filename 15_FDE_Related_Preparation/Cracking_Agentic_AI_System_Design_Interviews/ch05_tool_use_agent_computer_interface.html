Running example: a support agent that can search orders and issue refunds. We'll keep coming back to it as each piece of this chapter gets added.

The Agent-Computer Interface

Everything your agent can see and touch — its tools, their schemas, what comes back, and who's allowed to call what. That whole surface is called the agent-computer interface (ACI), and it sets the ceiling on how reliable the agent can ever be.

Treat your tools like a public API for a partner who can't read your docs and can't ask you a question. Our support agent doesn't know search_orders returns null for "no such order" vs. "database is down" — unless you tell it, explicitly, every time.

Our issue_refund call just failed — why, really?
flowchart TD A["Our agent calls issue_refund and it fails"] --> B{Why, really?} B --> C1["1. Wrong tool: it called cancel_order by mistake"] B --> C2["2. Right tool, bad args: sent a string, needed a number"] B --> C3["3. Looked fine, wasn't: refund exceeds what was paid"] B --> C4["4. It worked, but the result was unusable"] B --> C5["5. The model just messed up (rare once 1-4 fixed)"]
  • Only #5 is a model problem — the other four are bugs in your design, not the LLM's judgment.
  • If refund calls succeed less than ~90% of the time, don't reach for a bigger model — fix the interface first.
🎯 OpenAI Interview Pointer Naming this order out loud — "I'd check the interface before blaming the model" — is exactly the kind of judgment call a system-design panel wants to hear. It signals you've actually debugged a tool layer, not just read about one.

Eight Rules of Tool Schema Design

A checklist that fixes most tool failures before you ever touch the model.

Say we're writing issue_refund for our support agent. Here's what changes, rule by rule.

issue_refund, before → after
RuleBeforeAfter
1. Name the actionordersV2Querysearch_orders
2. Say what NOT to use it for(nothing)"Do NOT use for refunds — call issue_refund"
3. Constrain everythingstatus: stringenum[open,shipped,...]
4. Units in the nametimeouttimeout_seconds
5. Flat, ≤6 argsfilters: {...}order_id, reason, amount_cents
6. Small resultsfull 40-field record6 fields it actually needs
7. Teachable errors400 Bad Request"end_date is before start_date"
8. Idempotent writesrefunded twicesame key → refunded once
  • Every constraint (an enum, a bound) is one more mistake the model literally can't make.
  • Rule 8 alone stops the "agent retries and double-refunds the customer" incident before it happens.

Typed Results: The Five States That Matter

Instead of a tool just returning a string, give it a typed result with five possible states — SUCCESS, EMPTY, UNAVAILABLE, DENIED, INVALID. This one change fixes more agents than anything else in this chapter.

Our agent searches for an order and gets nothing back. Was there genuinely no matching order (EMPTY), or is the database just down (UNAVAILABLE)? If your tool can't tell these apart, neither can your agent — it'll just keep rewording the same query through a real outage until it burns through its whole budget.

What actually happened?
flowchart LR Call([Agent calls a tool]) --> R{What actually happened?} R --> S["SUCCESS - here's your order"] R --> E["EMPTY - searched fine, nothing matched"] R --> U["UNAVAILABLE - database is down"] R --> D["DENIED - not allowed"] R --> I["INVALID - bad input, here's the fix"]
  • Mixing up EMPTY and UNAVAILABLE causes retry storms during a real outage.
  • Mixing up DENIED and INVALID teaches the agent to work around your policy.
Deep Dive: never explain a denial
Say issue_refund returns DENIED with "refunds over $500 need manager approval." The agent reads that as an instruction, not a wall — next time it wants to refund $600, it just issues two $300 refunds instead. Denials should be a dead end to the model, fully explained only in the trace a human reads later. It's deliberate, and interviewers like to probe it.
🎯 OpenAI Interview Pointer "How would you design your tool's result types?" is a near-certain question. These five named states, plus the refund-splitting failure above, is the specific detail that separates a strong answer from a vague one.

The Tool Gateway

One single doorway between the agent and anything real happening in the world. Every call — refund, lookup, anything — walks through the same seven checks, in the same order, no exceptions.

issue_refund, walking through the gateway
sequenceDiagram participant O as Orchestrator participant G as Gateway participant P as Policy participant V as Validator participant T as Tool/API O->>G: call issue_refund(order_123, $50) G->>P: allowed to refund? P-->>G: allow / DENIED G->>V: args match schema? V-->>G: valid / INVALID G->>T: call, timeout + idempotency key T-->>G: result or error G-->>O: classified, trimmed ToolResult
  • Order matters: authorize before you validate. Otherwise a denied caller learns the schema from the validation error.
  • Idempotency key = hash of run_id + tool_name + arguments — call twice with the same key, refund happens once.
  • Trim results to what's declared. One real team's support-agent cost doubled overnight — and got 9s slower — when a backend added 14 fields and the tool returned all of it, unfiltered.
🎯 OpenAI Interview Pointer "How do you stop an agent from doing something it shouldn't?" — the strong answer names the mechanism (authorize → validate → idempotent call → trim → log), not "we add guardrails."

The Model Context Protocol (MCP)

A shared protocol for handing an agent its tools, its data, and its prompt templates — instead of every team writing a one-off integration for every tool, everyone speaks the same client-server language.

Without it: 5 apps × 10 tools = 50 custom integrations. With MCP: 5 clients + 10 servers = 15 pieces. That gap only grows.

Our agent's runtime, talking to two servers
flowchart LR subgraph Host["Our agent's runtime"] C1["MCP Client to Orders"] C2["MCP Client to Warehouse"] end C1 -- stdio --> S1[Orders Server] C2 -- streamable HTTP --> S2[Warehouse Server]
  • Tools — the agent decides to call them, can have side effects (like issue_refund).
  • Resources — the host app decides what goes in, addressed by URI, no side effects (like a policy doc).
  • Prompts — the user invokes them on purpose (a slash command).
  • Expose a document library as a "tool" and the model calls it repeatedly, burning budget. As a "resource," the host controls what enters context instead.
  • stdio = subprocess, no network, one developer's laptop. Streamable HTTP = real network service, real auth, the only sane choice once shared.
Deep Dive: two ways MCP quietly breaks security
Confused deputy — the server runs with its own (often broader) credentials. If you don't pass the real user's identity through and check it server-side, your agent can do anything any user could do, for any user.

Cross-server data flow — one client on a private data server, another on a public web-search server, and you've built a leak path. (Preview of Ch. 16's "lethal trifecta.") Keep servers in different trust domains on separate clients.
🎯 OpenAI Interview Pointer MCP sits right in the "Tools & Protocols" part of most evals. Explain the three primitives by who's in control (model, app, or user) — not "a way to plug in tools."

Tool Selection at Scale

The more tools you hand the agent, the worse it gets at picking the right one — it's discriminating between similar-sounding options inside a fixed attention budget.

Our support agent has 200 internal APIs behind it, not just two. Here's how you keep it sane.

Four composable strategies
StrategyWhat it meansExtra latencyUse when
Principal filteringOnly show tools this caller can usenonealways
NamespacingOne façade + operation enumnonelots of similar ops
RetrievalEmbed, pull top-k per request20-60ms> ~40 tools
Hierarchical routingSmall router picks domain firstone extra callgenuinely distinct domains
  • Split façades by who's allowed to do what, not by which service it hits — never bundle a write and a read together.
  • Watch two numbers separately: right tool picked? right arguments filled in? Consolidating tools tends to help the first and can quietly hurt the second.
Deep Dive: the "200 tools" design question
A real interview drill from the book. Strong answer: don't advertise 200 tools — collapse reads behind scope-based façades first (→ 20-40), filter by who's calling, add retrieval only past ~40 tools. Keep a couple of tools pinned and always visible — like clarify and escalate — so the agent is never stuck. Always check the real user's permissions server-side.
🎯 OpenAI Interview Pointer This exact "200 tools" scenario is a stock system-design prompt. Open with "collapse the surface first" — most candidates jump straight to embeddings and skip the façade/authorization design that actually shows judgment.

Sandboxing Code Execution

If your agent can run arbitrary code, that's the single most dangerous tool you can give it — you can't validate your way to safety, because there's no way to know in advance what code will do. Isolation is the only real answer.

Imagine a data-analysis agent that writes Python to answer "top 10 refund reasons last month." Now imagine someone tricks it into running os.system('rm -rf /') instead.

Six isolation controls
flowchart TD Code[Agent-written code] --> Iso["Container: read-only root, one writable folder, non-root user"] Iso --> Net[No network, by default] Iso --> Res[Hard limits: CPU, memory, processes, wall-clock kill] Iso --> Cred[No cloud credentials, no ambient secrets] Iso --> Life[Destroyed after this one run] Iso --> Out[Output truncated]
  • Six controls, none of them "ask the model nicely": isolate, no default network, resource caps, no ambient creds, single-use, truncated output.
  • A static check blocking os.system/eval/exec is a nice extra layer — never the main defense.
Deep Dive: what this looks like in practice 
docker run --rm --network none --read-only \
  --tmpfs /work:rw,size=256m,noexec \
  --user 65534:65534 --memory 512m --cpus 1.0 \
  --pids-limit 128 --cap-drop ALL \
  --security-opt no-new-privileges \
  agent-sandbox:python-3.12 timeout --signal=KILL 30s python /work/task.py
Every flag maps to one of the six controls above — this is what "isolation" actually looks like, not a hand-wave.
🎯 OpenAI Interview Pointer "Someone tricked your code-interpreter agent into running rm -rf / — how, and how do you stop it?" is a documented interview question. Strong answer: you can't count on the model refusing every time — sandboxing is the actual control.
