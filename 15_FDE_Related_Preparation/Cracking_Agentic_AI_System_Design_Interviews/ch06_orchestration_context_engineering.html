Orchestration and Context Engineering

Who decides what happens next, and what does the model actually see when it decides? Both are budgets you spend on purpose, not by accident.

Control Placement 6 Topologies 4 Operations Deterministic Assembly Context Rot Cheat Sheet
Running example: an internal ops agent with write access to a config service, used by about sixty engineers. Every request raises the same question: what happens next, and who decides?

Control Is a Resource You Allocate

Every step an agent takes was preceded by a decision about what to do next, and that decision can live in one of three places: fixed code, a small model, or the reasoning model itself.

When our ops agent gets "bump the timeout on service X," you could let the big model decide everything — or push that decision down to something cheaper and more predictable, saving the big model for cases that actually need it.

Where can this decision live?
WhereCostTestable?Handles novelty?
In code (fixed edge)FreeFullyNo — only what's anticipated
In a small model (router)CheapAgainst a labeled setOnly within defined labels
In the reasoning modelA full model callResists testingYes
  • Most systems put far more decisions in the reasoning model than they need to, purely for convenience — then pay for it on every request, forever.
  • The habit worth building: for each decision, ask "could this live one level down?"
🎯 OpenAI Interview Pointer The book calls this out directly: a candidate who audits decisions this way reads as someone who has actually operated a system at cost, not just designed one on a whiteboard.

Six Orchestration Topologies

Six repeatable shapes cover how agent systems structure "what happens next" — and real systems almost always compose more than one.

For our ops agent: a config request gets classified (router), known types run a fixed workflow (sequential), anything ambiguous drops into a bounded loop, and a step needing three lookups fans them out in parallel.

Pick the shape by its trigger condition
TopologySelect whenLatencyDominant risk
SequentialSteps known, strictly orderedSum of stepsRigid, no recovery
RouterIntents enumerable, disjoint+1 small callSilent misroute
Parallel fan-outSubtasks independentSlowest branchMerge conflicts, cost×
Bounded loopNext step needs last observationVariableOscillation, no progress
HierarchicalDistinct specialities/scopes+overhead/hopCoordination > benefit
Event-drivenAsync, long horizonsDecoupledOrdering, duplicates
  • Realistic production shape: event consumer → router classifies → most run sequential → residual enters a bounded loop → the loop fans out in parallel for retrieval.
  • Track traffic share of each path continuously. Router drift — more traffic silently sliding into the expensive loop — is the most common silent quality regression in production agents.
Deep Dive: the composed orchestrator pattern
A router (small model) checks confidence and complexity. High confidence + low complexity → run the matching deterministic workflow. If it fails structurally, escalate to the bounded loop once — bounded, so a broken workflow can't silently double-spend on every request forever. Every routing decision is logged as a metric dimension, not just a log line, because router drift is invisible without that time series.
🎯 OpenAI Interview Pointer Naming this composition explicitly — "I'd compose these, not pick one" — is stronger than naming a single topology, because it's what production systems actually look like.

Context Engineering: The Four Operations

Context engineering is deciding exactly what goes into the model's context window at each step, under a fixed token budget, on purpose. It replaced prompt engineering as the core skill, the same way schema design replaced query tuning.

Every context strategy reduces to these four
flowchart TD W["Write: persist outside the window
(scratchpad, run state, long-term memory)"] --> CTX((Context Window)) S["Select: pull in only what THIS step needs
(per step, not per run)"] --> CTX C["Compress: shrink what must be kept
but not verbatim"] --> CTX I["Isolate: hand a subtask its own window,
return only the conclusion"] -.-> CTX
  • Write early — anything not written down can't survive a compaction pass.
  • Select per step, not per run — a tool result useful at step 2 is noise by step 7.
  • Compress is lossy by definition — choose what to lose on purpose (structured extraction beats prose summary beats blind truncation).
  • Isolate is the strongest, most underused lever — see below.

Deterministic Context Assembly

Assemble every step's context in a fixed section order, with a fixed token budget per section — and when something has to go, cut inside a section, never across the whole window.

For our ops agent, a step's context always looks the same, in this order:

Fixed order, fixed caps — only the caps move
flowchart TD A["System instructions & policy — 800 tok, NEVER evicted"] B["Tool schema, filtered — 1200 tok"] C["Durable facts & profile — cap 600 tok"] D["Retrieved evidence — cap 5000 tok"] E["Compressed history — cap 1500 tok"] F["Recent turns, verbatim — cap 3000 tok"] G["Current goal — 200 tok, NEVER evicted"] A --> B --> C --> D --> E --> F --> G
  • Order buys cacheability. Providers cache a prompt prefix only if it's byte-identical across requests — instructions and tool schema first, nothing inserted above them, turns a large share of input tokens into cheap cache hits.
  • Order buys debuggability. A deterministic assembler means you can reconstruct exactly what the model saw at any step from the trace alone.
  • When a section overflows, trim within it and leave an explicit marker — never silently pretend the content never existed.
Deep Dive: the bug that will not stay fixed by accident
The most common context bug: "if too long, drop from the front." Since instructions sit at the front, a long-running agent quietly loses its policy and safety constraints — and starts behaving like a general assistant holding production credentials. Global truncation deletes your instructions. The fix is structural, not "be careful": mark instructions and the current goal non-evictable, evict only inside the other sections.

Context Rot and Sub-Agent Isolation

Model accuracy degrades as the window fills, and unevenly — information stuck in the middle gets retrieved less reliably than information at either end. Three well-chosen observations often beat twelve.

Shared context vs. isolated sub-agents
flowchart LR subgraph Shared["Shared context, 3 subtasks"] P1["Parent accumulates
tens of thousands of tokens"] --> P2["...resent on every later step"] end subgraph Isolated["Sub-agent isolation"] S1["Each subtask gets its own window"] --> S2["Parent gets one short
conclusion each"] S2 --> S3["Parent grows by ~1,000 tokens total"] end
  • Isolate when a subtask's intermediate steps aren't needed downstream — research, verification, extraction.
  • Share only when steps genuinely need to reason across each other's intermediates — rarer than it feels.
  • On a real ten-step run, isolating typically cuts billed input tokens by an order of magnitude.
  • What you give up: auditability across the boundary. Link the sub-agent's full trace from the parent's span.
Deep Dive: The Agent That Forgot Its Own Safety Policy at Step Nine
A real production incident — this chapter's own ops agent. It behaved correctly on short runs, but past ~8 steps it started approving config changes its own policy prohibited, including production edits outside the change window. Cause: the context builder truncated from the front once things got long, and the safety policy sat at the front — gone entirely by step nine. The team's evaluation suite only used short scenarios, so the bug was invisible to every test they had. Fix: sectioned assembly with non-evictable instructions, in-section eviction, an assertion that the policy hash is always present — and a new standing requirement to test any write-access agent on runs past the compaction threshold.
🎯 OpenAI Interview Pointer "Answer quality degrades on long runs but every component tests clean" is a documented interview drill in this book. Strong answers reconstruct exactly what the model saw before guessing, check instruction eviction first, then context rot — most candidates jump straight to "the model isn't good enough."
