The Forty-Five Minute Script

Time is the binding constraint. Twenty minutes on requirements produces an incomplete design; two minutes produces a generic one. Rehearse against a clock until the pacing is automatic.

Seven phases, forty-five minutes
flowchart LR A["0-8 min
Requirements: 8 numbers,
oracle, scope cut"] --> B["8-12 min
State schema
+ action space"] B --> C["12-20 min
Control pattern,
draw architecture"] C --> D["20-28 min
Failure ladder,
safety, human gates"] D --> E["28-35 min
Scale, cost
arithmetic, capacity"] E --> F["35-41 min
Measurement
and rollout"] F --> G["41-45 min
Your questions"]
  • Miss the first 8 minutes and every later answer is guesswork. Miss the last 5 and you forfeit the leveling signal.
  • Three opening moves, every time: restate the problem in one sentence, ask for the eight numbers (throughput, latency, horizon, accuracy, cost, autonomy, data class, recovery), name the oracle and cut scope.
🎯 OpenAI Interview Pointer Close requirements by restating everything as one sentence, then ask "is that the system?" Twenty seconds, consistently marked as a strong signal — it's what a technical lead does at the start of a real project.

Worked Design One: A Deep Research Agent at Consumer Scale

A read-only, citation-grounded research agent for ~100K daily users — walked through the same script, with the arithmetic said aloud.

Untrusted web content stays isolated from user documents
flowchart TD Q[Question + cache probe] --> P["Plan (reasoning tier):
decompose?"] P --> W["Web sub-agents
(untrusted, NO user doc access)"] P --> D["Document sub-agent
(user-scoped)"] W --> S["Schema boundary -
typed findings only"] D --> S S --> L["Evidence ledger
(user-scoped, dedups sources)"] L --> G[Grade coverage + agreement] G --> Y[Synthesize with citations] Y --> V[Verify claims against evidence] V --> O["Streamed answer + citations
+ coverage note"]
  • Requirements: ~40K runs/day (peak 3x), p95<90s with first signal <3s, 3-12 step horizon, success = every claim cited, $0.20/run ceiling, read-only (no approval subsystem needed — say so explicitly).
  • State: run/user identity, goal, dependency-aware plan, evidence list with a concatenating merge rule (prevents Ch.2's fan-out data-loss defect), tool errors, draft, verification score, budget summed across branches.
  • The arithmetic: 40K/day peaked 3x ≈ 100 runs/min; Little's Law → ~120 in-flight at p95=70s → size concurrency ~170 at 70% utilization. Naive cost ≈30K input tokens/run — fixed by sub-agent isolation (biggest lever), prefix caching, tier routing.
  • Safety, volunteered unprompted: no external comm tool, so trifecta's 3rd leg seems absent — except the rendered answer itself is a channel, so an egress firewall on rendering is mandatory. Web sub-agents hold zero document scope — an injection can't reach the private corpus even in principle.
  • Falsifying metric: the grade distribution. Most runs grading poorly even after correction means the corpus, not the architecture, is the constraint.

Worked Design Two: An Incident Response Agent for an SRE Team

A write-capable, high-stakes agent under a 30-second latency floor — same script, entirely different risk profile.

Read-only investigation, staged mitigation
flowchart LR A["~1,200 alerts/day
(bursty during incidents)"] --> B["Dedupe + correlate
BEFORE any model call"] B --> C["Read-only investigation
(query anything, change nothing)"] C --> D["Proposed mitigation:
command + blast radius + evidence"] D --> E["Human approves
(~10s fine mid-incident)"]
  • Read-only investigation, staged mitigation: a 10s human approval mid-incident is fine; an autonomous rollback on a wrong hypothesis is not.
  • Dependency inversion: the agent depends on the observability stack, which is disproportionately likely to be degraded during the very incident it's investigating — every telemetry query can return EMPTY/UNAVAILABLE, and source coverage is a first-class output field.
  • Burst capacity: 1,200 alerts/day is trivial; 400 in 90 seconds during an incident is not — dedupe/correlate before any model call, cap concurrent investigations per service.
  • Falsifying metric: hypothesis precision. Below a threshold, responders stop reading the output — an ignored tool is worse than none.
🎯 OpenAI Interview Pointer Both worked designs volunteer the safety/trifecta analysis before being asked. That's a deliberate, repeated signal in this book: naming the security boundary unprompted reads as senior threat modeling, not box-checking.

Follow-Up Questions and the Shape of a Strong Answer

The interviewer's follow-up bank — and what separates a real answer from a generic one.

Eight common follow-ups
Follow-upShape of a strong answer
Scale to 10x?Name the binding constraint first (usually provider quota), then arithmetic, then the lever + its cost
What breaks first?A specific component + specific symptom + the metric that reveals it — never "hallucinations"
How do you know it works?The oracle, sampled online measurement, offline gate, and the offline suite's power limitation
What if the model gets worse?Version pinning, eval before adoption, canary+guardrails, auto rollback, 2nd provider behind an adapter
How much does it cost?Per-run arithmetic derived aloud, blended figure, levers with expected effect
Where's the security boundary?The gateway, the trifecta analysis, egress control on tool path AND rendering path
Cut for a 2-week version?A reduced scope that still has an oracle + failure ladder — and what you would NOT cut, and why
Handle a bad actor?Rate limits, per-principal cost governor, anomalous tool-sequence detection — prompt defenses are rate-reducers, not boundaries
🎯 OpenAI Interview Pointer "What breaks first" is worth rehearsing most. Wrong shape: "hallucinations." Right shape: "the search tool returns empty during a partial outage, the agent treats empty as valid, we ship uncited claims — signal is citation-free answer rate, fix is a typed result distinguishing empty from unavailable." A symptom, a mechanism, a metric, and a fix — in one breath.

The Levelling Rubric

What each level actually sounds like out loud — a description of what to say, not a judgment of who you are.

Mid → Senior → Staff, in what's said
LevelSounds likeMissing
MidCorrect components, names a framework, working happy pathNumbers, failure design, trade-offs as choices
SeniorRequirements as numbers, names the control pattern AND the rejected alternative, degradation ladder, cost arithmeticOrg consequences, migration path, second-order effects
StaffAll of the above, plus: what to build first and why, what to deliberately NOT build, how it changes at 10x, the falsifying metricLittle — differences are about scope of influence
Deep Dive: depth on one component vs. breadth across the design
Cover the whole design at consistent depth first, then offer depth explicitly: "I can go deeper on the evaluation layer or the cost model — which is more useful?" Letting the interviewer choose beats guessing. Candidates who go deep unprompted usually pick the component they know best (not the one being assessed), and run out of time before the failure/measurement sections — exactly where the leveling signal lives.
