1 · What the Decomposition Round Actually Is

Borrowed from Palantir's playbook and now standard at OpenAI for Applied AI / FDE-type roles.

A 45–60 min open-ended session: you get a vague, real-world enterprise problem and must break it into users, data, workflows, constraints, and a prioritized V1 — out loud, collaboratively. There is no correct answer; interviewers watch how you navigate when the path is undefined. It eliminates more qualified candidates than any other stage — not because the problems are technically hard, but because engineers who crush LeetCode in silence freeze when the interviewer keeps adding constraints mid-stream.

Failure mode #1
Jumping to architecture before clarifying scope. An OpenAI FDE candidate reported the interviewer literally stopped them and asked: "What questions would you ask the customer before designing anything?"
Failure mode #2
Hand-waving evaluation. "How do you know your AI system is actually working well?" is used as a deliberate differentiator — most engineers fumble it. This maps directly to the evaluation-best-practices doc OpenAI sends candidates.
What they score
Continuous narration of reasoning — a polished answer delivered in silence scores worse than messy, well-narrated thinking. Asking the right questions before committing to an approach mirrors the actual job.

2 · Tier 1 — Most Likely Prompts 19 questions

Reported or representative prompts. Expect a variant: an ambiguous business problem where an agentic system is the implied solution.

A. Reported decomposition prompts (OpenAI / FDE-style)

OpenAI · FDE1

"A logistics firm wants an AI agent to handle automated shipment rerouting. They have SAP data, real-time weather APIs, and 500 warehouse managers on different regional systems. How do you build it, and how do you evaluate it?"

Tests: multi-system data unification, stakeholder surface area, and whether evaluation is first-class in your answer.

Decomp classic2

"A major city wants to reduce 911 emergency response times. They have call data, traffic sensor data, and ambulance GPS data. You have 60 minutes. Go."

Tests: mission clarification (response time vs. cost vs. equity of coverage), input mapping, sequencing by risk.

Decomp classic3

"A regional bank wants to unify fraud detection across three legacy systems acquired through M&A. None of the data is labeled consistently. How do you scope the first 90 days?"

Tests: data quality realism, phased scoping, regulatory constraints.

Decomp classic4

"A hospital network wants to reduce medication errors in post-surgery care. They have patient records, pharmacy dispensing logs, and nurse assignment schedules. Where do you start?"

Tests: high-stakes HITL design, safety-first decomposition.

OpenAI · perf5

"A customer demands sub-100ms latency for an LLM-powered search. The naive RAG flow is 1.5 seconds. Walk me through getting to 100ms."

Tests: latency budget decomposition across retrieval, generation, and network.

Pattern to notice
Every prompt is business-goal-first, data-second, model-last. Nowhere is the question "which model would you use?" — it's always "here's a messy org and its data; decompose the path to a working, evaluable system."

3 · Tier 2 — Deep-Dive Probes That Follow Your Design 27 probes

Once you propose an architecture, interviewers drill into these clusters (from the r/ExperiencedDevs agentic-design thread and 40-question agentic guides).

Agent loop & orchestration

  1. What logic belongs in the orchestrator vs. the LLM itself?
  2. How do you design a safe, debuggable agent loop? What are the termination conditions for long-running agents?
  3. Stateless vs. stateful agents — tradeoffs?
  4. How do you detect and stop infinite planning loops?
  5. How do you prevent over-reasoning / over-planning?
  6. How do you version and roll back agent behavior (and prompts) in production? How do you A/B test them?

Tool use & execution

  1. How do agents decide which tool to use? How do you design tool schemas that reduce hallucinated actions?
  2. How do you handle tool failures, retries, idempotency?
  3. How do you sandbox tool execution?
  4. How do you control cost explosions from runaway tool calls?

State, memory & data

  1. How do you manage state across async, multi-step workflows? see §5
  2. Working / episodic / semantic memory — when do you retrieve vs. ignore?
  3. How do you keep long-term memory from getting polluted?
  4. Customer data split across SAP + Salesforce + Postgres — how do you unify it for an agent?

Multi-agent

  1. When is multi-agent actually better than single-agent — and when does it just add cost and failure modes?
  2. How do agents coordinate without conflicting actions?
  3. How do you debug failures across interacting agents?
  4. Cheap-model routing before LLM fallback for edge/ambiguous cases — latency + cost optimization?

Evaluation & observability highest-signal for OpenAI

  1. Design an evaluation harness for an agent with a 99% task-success target.
  2. Offline + online evals, golden sets, LLM-as-judge biases, regression-testing prompts.
  3. Design observability for an agent system: what do you log, alert on, dashboard? Trajectory analysis? Correlation IDs and replay?
  4. How do you detect goal drift or misalignment?
  5. What metrics matter beyond task success?

Safety, guardrails & human-in-the-loop

  1. Prompt injection (direct & indirect), PII filtering before data hits the LLM, capability isolation.
  2. When do you route to human-in-the-loop?
  3. How does auditing/logging drive HITL decisions?
  4. Circuit breakers, rate limiting, graceful degradation when the model is unavailable.

4 · The Framework That Wins the Round

Narrate this structure explicitly — Exponent and Final Round AI converge on the same six steps.

Clarify the mission (3–5 min)
Before scoping anything, ask: "Are we optimizing for response time, cost, accuracy, or equity of coverage? Who's the primary user?" State assumptions explicitly if they don't confirm.
Stakeholders & success metrics
Who calls this a success, and which number moves?
Map the inputs
What data exists, what shape, who owns it, how fresh? Data-oriented thinking is an edge — lean into data quality and lineage.
Decompose into workstreams, sequence by risk
E.g., (a) data ingestion/quality, (b) the agent/model layer, (c) the operator-facing surface. Justify the ordering.
Walking-skeleton MVP, then iterate
Ship the thinnest end-to-end version — even with mocked agent logic — to prove the integration story, then swap in real components.
Adapt live
The interviewer will change a constraint mid-round ("you lost access to the GPS feed"). Re-derive without defending your original plan — adaptability is what's being scored.
Two differentiating habits
1. Think out loud continuously — narrate tradeoffs as you make them. 2. Tie every design choice back to how you'd evaluate it — this maps directly to the evaluation-best-practices guide OpenAI sent you, and it's where most candidates hand-wave.

5 · State Management in Async, Multi-Step Workflows

The deep-dive probe you're most likely to face as an agentic candidate — full answer, ready to narrate.

The problem: an agent's workflow isn't one request-response — it's a chain of steps (plan → tool call → wait → next step) spanning minutes, hours, or human approvals. Each step is async and can fail, retry, or pause. The workflow must survive crashes, resume correctly, and never execute a side-effect twice.

The five rules

  1. Externalize state, keep workers stateless. Never hold workflow state in process memory. Persist it (Postgres, Redis, DynamoDB) after every step. Any worker can pick up where the last one left off — crash-safe and horizontally scalable.
  2. Model state as an event log, not just a snapshot. Record each step append-only (task_received → plan_created → tool_called → result_stored). Replaying the log reconstructs full context — critical for debugging agent decisions and resuming after failure.
  3. Idempotency + exactly-once semantics for side effects. Every step gets a unique ID. Before executing a real-world action (payment, email, DB write), check whether that step ID already ran. Async retries will happen — idempotency keys make them harmless.
  4. Explicit state machine over implicit control flow. Define states (PENDING → RUNNING → WAITING_HUMAN → COMPLETED / FAILED) and legal transitions. The orchestrator advances state based on events; async steps (tool calls, human approvals) are just waiting states with timeouts. This is how Temporal, LangGraph, and Databricks Workflows handle it.
  5. Handle the async gaps deliberately. Long-running steps use queues + callbacks (or polling with backoff); timeouts trigger escalation/compensation; human-in-the-loop pauses are just another persisted state — not a blocked thread.

The one-line interview answer

"I keep workers stateless, checkpoint progress to durable storage after every step as an event log, make all side-effects idempotent, and model the workflow as an explicit state machine — so any step can fail, retry, or wait on a human without losing context or double-executing."

Two implementation gotchas (interview gold)

  • RetryPolicy needs explicit retry_on — with defaults, a plain ValueError is not retried in LangGraph 1.x; only explicitly matched exception classes are.
  • For replay/fork, reuse the checkpoint's own config object — a hand-built {"configurable": {"thread_id":..., "checkpoint_id":...}} dict misses checkpoint_ns and crashes update_state() with a KeyError.
Production checkpointer progression
InMemorySaver for tests → SqliteSaver for local dev → PostgresSaver (or a platform-native store, e.g. Databricks/Temporal-backed) for production. Same code — swap the saver.
