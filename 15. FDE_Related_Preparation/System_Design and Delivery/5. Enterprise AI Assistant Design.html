Define the problem space

Clarify before you architect

Employees should be able to ask things like "What's my remaining vacation balance?", "Create a Jira ticket," "Show last month's sales," or "Book a meeting room" — and the assistant has to integrate with over 100 internal applications to answer them. Before reaching for architecture, a strong candidate clarifies scope: is this read-only, or can it act? Do the backend systems already speak REST, or is there GraphQL, SOAP, and legacy SQL mixed in? Does it need to chain multi-step requests like "Schedule a meeting with John and send him the latest proposal"? And critically — does every employee see the same data, or does Finance need to stay walled off from HR?

Five clarifying questions reshape the design before a single box gets drawn: read and write access, integration diversity across REST/GraphQL/SOAP/legacy systems, multi-step reasoning (which implies an orchestration layer, not just function calling), scale — 50,000 employees globally with ~8,000 concurrent at peak — and per-department permissions that make identity propagation a first-class design requirement.

What the assistant must do

The qualities that make it production-grade

High-level architecture

One request, three ways to reach the backend

A request flows from the employee through the chat UI, an authentication layer, and an AI Gateway to an LLM-driven Planner Agent — which is where the interesting decision happens. Rather than picking one integration technology, the Planner reaches business applications through three complementary paths: direct function calls, MCP servers, and REST APIs, chosen per-task rather than globally.

3

Three integration methods

Why not just call REST APIs directly?

Because each integration style solves a different problem — REST, function calling, and MCP are complementary rather than competing technologies. Reaching for only one of them eventually breaks the system in a predictable way.

🌐 REST APIs

GET /employees/123 · POST /jira/ticket · PUT /vacation/request

Ideal when the interface is stable, the application already exposes APIs, operations are deterministic, and no AI reasoning is needed. Fast, mature, easy to monitor — the enterprise standard. But LLMs don't naturally understand authentication, endpoint discovery, request schemas, or parameter validation, so REST alone never adds up to an intelligent assistant.

🧰 Function calling

createTicket() · getVacation() · bookMeeting()

Works well when the number of tools is small — the model can reasonably choose among twenty functions. But scale that to 1,500 functions across 100 applications and it breaks: prompt size explodes, tool selection gets inaccurate, every schema has to be maintained and re-embedded into prompts. Function calling doesn't scale well by itself.

🔌 MCP (Model Context Protocol)

SAP MCP Server · Jira MCP Server · Salesforce MCP Server · HR MCP Server

MCP solves the discoverability problem. Instead of exposing 1,500 tools directly to the model, each application exposes one MCP server that advertises its resources, tools, prompts, and capabilities — the assistant asks "what tools do you expose?" instead of hardcoding createInvoice(), approveInvoice(), cancelInvoice() one by one. This is a common point of confusion: MCP doesn't replace REST — REST remains the transport. MCP provides a standard AI interface over existing capabilities, and internally an MCP server may call REST, SOAP, SQL, Kafka, GraphQL, or a legacy system. REST solves communication; MCP solves AI interoperability.

These three aren't parallel transports — they're layers, and function calling's implementation is usually just a REST call underneath. The axis that actually separates REST from function calling is who decides to make the call, not how the call happens on the wire. REST-as-a-path means fixed application code already knows exactly which endpoint to hit — no model reasoning involved (the vacation page calling GET /employees/123/vacation when it renders). Function calling means the LLM itself decides, from natural language, whether to invoke something and with what arguments (a user asking "how many vacation days do I have left?" → the model decides to call getVacation(employee_id, before_date)) — and that function's implementation is very often the exact same REST endpoint underneath. Same wire call, two different layers, because they carry different costs: adding another REST endpoint is cheap, but adding another function the model must choose between costs prompt space and tool-selection accuracy — which is exactly the ceiling MCP exists to remove. The full stack, bottom to top: REST/SOAP/SQL (what actually executes) → function calling (the model's mechanism for deciding to invoke one thing) → MCP (how the model discovers which functions exist without 1,500 hardcoded schemas) → agent framework (coordinates more than one such decision across a multi-step task).
4

Agent frameworks & orchestration

For work no single function call can coordinate

Agent frameworks earn their place when a request needs multi-step reasoning. "Prepare a renewal report for our top customers and email their managers" means finding customers, retrieving CRM data, generating a report, creating charts, storing a PDF, and sending an email — a single function can't coordinate that. Instead, a Planner Agent breaks the request into steps and hands each one to a specialist.

🟢 Single agent

One tool · short workflow · deterministic execution

Example: "Create a Jira ticket." One tool call, one clear outcome — an orchestrator would just be overhead.

🔷 Multi-agent

Planning required · many domains · independent specialists · long-running tasks

Example: "Analyze quarterly sales, identify declining regions, prepare a PowerPoint, notify leadership." Multiple domains, real planning, worth the coordination cost.

Scaling to 500+ applications

What breaks at 500 apps and 200,000 employees

1 · Tool discovery

Loading every MCP server up front doesn't scale. A Tool Registry loads only the relevant servers for the current task, keeping prompt size small.

2 · Caching

Frequently requested information — employee profiles, org hierarchy, holiday calendar — gets cached, cutting backend load for the common case.

3 · Horizontal scaling

Planner service, authentication, gateway, and LLM routing all stay stateless, running as multiple replicas behind load balancers.

4 · Rate limiting

User quotas, application quotas, and circuit breakers guard against runaway agents, accidental loops, and prompt abuse.

5 · Async execution

Long-running workflows return a "task accepted" response with a job ID instead of blocking the user — workers execute asynchronously.

6 · Security

Every request propagates user identity, an OAuth token, RBAC/ABAC, and audit logs. No application trusts the LLM — applications trust enterprise identity.

7 · Observability

Every execution produces a full trace — prompt → selected tools → reasoning trace → API calls → latency → cost → errors — which is what makes an AI system debuggable rather than a black box.

Global deployment follows the same stateless philosophy at a regional level: regional AI gateways close to users to cut latency, region-local MCP servers for apps hosted in each geography, a global identity provider with regional token validation, read replicas and regional caches for hot data, active-active deployment for stateless services with geo-DNS routing, and data-residency controls that keep sensitive HR or financial data inside its required jurisdiction.

Final design summary

Separating responsibilities instead of picking one technology

The architecture separates responsibilities rather than using one technology for everything. REST APIs remain the foundational integration mechanism — mature, performant, widely supported. MCP servers provide an AI-native abstraction over enterprise applications, enabling standardized tool discovery and easier onboarding without changing the assistant. Function calling invokes well-defined, deterministic operations once the right tool has been selected. An agent framework orchestrates complex, multi-step workflows that require planning, retries, parallel execution, and coordination across domains.

For scalability: stateless AI gateways, a tool registry, caching, asynchronous job execution, and horizontally scalable planner services. For security: enterprise identity propagated end-to-end, RBAC/ABAC enforced at the application layer, comprehensive audit logs, and an LLM that never bypasses existing authorization systems.

This layered architecture keeps the platform modular, scalable, and maintainable while allowing new applications to be integrated with minimal changes — treating REST, MCP, function calling, and agent frameworks not as competing technologies, but each used where it provides the greatest architectural value.

The 5-step framework

A repeatable structure for any system design interview

  1. Define the problem space

    Understand the problem and scope. Clarify functional and non-functional requirements. State assumptions and decisions explicitly.

  2. Design the system at a high level

    Design APIs to define how clients access system resources. Consider request parameters, response types, and client–server communication. Create a high-level diagram to illustrate the architecture.

  3. Deep dive into the design

    Examine system components and relationships in detail. Consider how non-functional requirements shape design choices. Present different design options with pros and cons.

  4. Identify bottlenecks and scaling opportunities

    Assess the system's ability to operate under load and support growth. Address single points of failure, data replication, global support, and scalability — sharding, CDN, caching, rate limiting, databases.

  5. Review and wrap up

    Summarize major decisions with justifications and tradeoffs. Confirm the design satisfies all requirements. Identify directions for further improvement.
