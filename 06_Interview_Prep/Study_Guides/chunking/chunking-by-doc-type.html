Chunking Techniques Across Document Types

What changes, why it changes, and how to pick a strategy per document type — with a live playground to see the boundaries move.

1. Why Chunking Isn't One-Size-Fits-All

Chunking decides what a retriever can possibly find. Get it wrong and no amount of embedding-model quality or reranking fixes it — the answer was never inside a single chunk to begin with.

  • Prose breaks cleanly at paragraph and sentence boundaries — sizing is the main lever.
  • Markdown / structured docs carry a header hierarchy that is the semantic structure.
  • Code becomes syntactically meaningless if a function is split in half by character count.
  • PDFs interleave body text, tables, and multi-column layouts that rarely match reading order.
  • HTML carries meaning in tags (<table>, <h2>) that plain-text splitting discards.
  • Tabular data isn't prose at all — splitting a row in half produces two meaningless fragments.
Rule of thumb: match the splitter's boundary awareness to the document's actual unit of meaning.

2. Core Parameters

Every splitter — regardless of doc type — tunes the same four knobs:

ParameterControlsTypical range
chunk_sizeMax unit length (chars or tokens)200–1500
chunk_overlapShared text between adjacent chunks10–20% of size

metadata preservationStructural context riding along with the chunkheaders, pages, row IDs

From text_splitters.py: RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50, separators=["\n\n","\n"," ",""]) tries each separator in order — paragraph breaks first, falling back to words, then raw characters. That fallback order is the boundary-awareness strategy every variant below builds on.

3. Document-Type Breakdown

3.1 Plain Prose

Splitter: RecursiveCharacterTextSplitter · Boundary: paragraph → sentence → word → char · Size: 500–1000 chars · Overlap: 10–20%

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", " ", ""],
)
PITFALLZero overlap silently breaks retrieval for facts that straddle a boundary — your own overlap_importance() demo shows the sentence split mid-thought at overlap=0.

3.2 Markdown / Structured Docs

Splitter: MarkdownHeaderTextSplitter + recursive second pass · Boundary: header hierarchy → char · Size: 500–800/section

headers = [("#","h1"), ("##","h2"), ("###","h3")]
splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers)
chunks = splitter.split_text(markdown_text)
# chunk.metadata -> {"h1": "...", "h2": "..."} — free, retrievable context
PITFALLA lone header-split pass can still yield a 5,000-char chunk if a section has no sub-headers — always chain a size-bounded second pass.

3.3 Source Code

Splitter: RecursiveCharacterTextSplitter.from_language() · Boundary: class → function → block · Size: 300–800 chars

python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON, chunk_size=500, chunk_overlap=50
)
PITFALLEven language-aware splitters don't understand indentation-scoped logic in a large class — consider AST-based chunking (one chunk per function/class) for big files.

3.4 PDFs (Mixed Layout)

Loader: PyPDFLoader / layout-aware alt · Splitter: recursive, on loaded Documents · Boundary: page → paragraph → char

docs = PyPDFLoader("./docs/demo.pdf").load()  # metadata={"page": N}
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
split_docs = splitter.split_documents(docs)  # metadata propagates
PITFALLMulti-column PDFs extract left-then-right columns interleaved wrong; tables flatten into disconnected fragments. Extract tables separately and chunk them as structured data (§3.6).

3.5 HTML

Splitter: HTMLHeaderTextSplitter · Boundary: DOM heading hierarchy → char

headers = [("h1","Header 1"), ("h2","Header 2")]
splitter = HTMLHeaderTextSplitter(headers_to_split_on=headers)
chunks = splitter.split_text(html_string)
PITFALLNav bars, footers, and ads get chunked alongside real content unless boilerplate DOM nodes are stripped first (target <main>/<article>).

3.6 Tabular / CSV Data

Splitter: none of the above — chunk by row, never by character count. Overlap: usually zero.

docs = [
    Document(page_content=row.to_json(), metadata={"row_id": i})
    for i, row in df.iterrows()
]
PITFALLThe single most common mistake: running a character splitter over a CSV, detaching the header row from data rows or cutting a row mid-column.

3.7 Semantic Chunking (Cross-Cutting)

Embed consecutive sentences, cut where similarity between neighbors drops — boundaries track topic, not character count. Best for transcripts and long-form docs where topic shifts ignore paragraph breaks. Trade-off: an extra embedding pass at chunking time.

splitter = SemanticChunker(OpenAIEmbeddings(), breakpoint_threshold_type="percentile")
chunks = splitter.split_text(long_text)

7. Databricks RAG Considerations

  • Vector Search granularity: chunk size determines what a single index hit returns — smaller chunks improve precision but can fragment context an LLM needs downstream.
  • Golden dataset alignment: re-run offline RAGAS/MLflow evaluation whenever chunking strategy changes — retrieval metrics are chunking-strategy-specific, not portable across strategies.
  • Lakehouse Monitoring / drift: a strategy that worked on early documents can silently degrade as new document types (e.g. table-heavy filings) enter the corpus — track this as a distinct drift signal.
  • Unverified boundary: table-heavy / multi-column PDF handling via Unstructured or Spark UDFs is worth flagging UNVERIFIED in accelerator docs until tested on the actual client corpus.

8. Pitfalls & Best Practices Checklist

  • Match splitter to the document's real unit of meaning — don't default to character-count splitting for structured or tabular content.
  • Never use zero overlap for prose; do use zero overlap for independent tabular rows.
  • Preserve structural metadata (headers, page numbers, row IDs) through the split.
  • For PDFs, validate extraction order before trusting chunk boundaries.
  • Re-run offline evaluation after any chunking strategy change.
  • For code, prefer language-aware or AST-based chunking over generic character splitting.
  • For tables embedded in prose/PDF, extract and chunk them separately from narrative text.
