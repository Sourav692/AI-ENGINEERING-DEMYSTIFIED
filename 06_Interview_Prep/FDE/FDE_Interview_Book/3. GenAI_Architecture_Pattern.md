
## 3.6 Skills and Dynamic Capability Loading — Cram Notes

- **Core idea:** A skill = more than a prompt — packages metadata (name/triggers/owner/version/permissions), instructions, knowledge, tools/scripts, and examples/evals for a recurring capability, so an agent doesn't load every domain into every request.
- **Progressive disclosure:** agent starts with a lightweight skill catalog → selects relevant skill → loads its instructions/resources → executes → releases context. Reduces context rot, keeps ownership modular.
- **Case study (home-improvement retailer):** one shower-tiling question routes through Project guidance (trades) → Materials-list (merchandising) → Delivery-window (fulfillment) — each team owns its own skill instead of one monolithic assistant knowing everything.
- **Loading contract pipeline:** user goal → select from lightweight catalog → authorize/load one skill → execute procedure+tools → validate artifact → unload task-specific context. Trigger descriptions need both positive *and* negative examples (counterexamples) to avoid wrong-skill activation.
- **Tool vs. Skill vs. Agent (distinct layers):** Tool = bounded callable (e.g., `get_inventory`), tested on contract/auth/failure. Skill = recurring procedure coordinating tools, tested on triggering/procedure/artifact quality. Agent = runtime actor deciding what to do next, tested on end-to-end decisions/recovery/stop behavior.
- **Governance:** give every skill an owner+version; test triggering separately from execution; scope permissions tightly; never auto-promote one successful trace into a permanent skill without review.

**Quiz answers:** Main value of dynamic skill loading → loads relevant capability without flooding every request with all domain context. Who should own a fulfillment skill → the team responsible for fulfillment rules/systems. What to evaluate separately → triggering and execution quality.
