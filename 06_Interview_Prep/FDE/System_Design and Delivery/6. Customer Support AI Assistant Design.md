# Customer Support AI Assistant Design

*System Design & Delivery Interviews — Reference*

The interview question: design an AI Customer Support Platform — like Salesforce Einstein plus Zendesk plus AI agents — that answers FAQs, creates and updates tickets, queries CRM systems, processes refunds, and escalates cases. Explain when you'd reach for **RAG, agent orchestration, tool calling, MCP servers, human approval, and memory**, and the tradeoffs each one carries.

`1M conversations/day` · `6 core technologies` · `3-layer memory` · `end-to-end architecture`

---

## 1 · Define the problem space

**A strong candidate clarifies before proposing an architecture.**

Customers should be able to ask product questions, track orders, request refunds, create and update support tickets, and escalate complex issues to a human agent. That's already both an information-retrieval system and a transactional one — and the clarifying questions that follow decide most of the architecture before a single box gets drawn.

> Is the AI only answering questions, or executing actions too — **both**. Where does product knowledge live — spread across documentation, a knowledge base, CRM, order management, and ticketing, which is exactly the shape RAG is built for. Can the AI make business decisions independently, like issuing a $5,000 refund — no, some actions need manager approval, which means human-in-the-loop workflows for sensitive operations. Scale — about one million conversations a day globally, which makes cost optimization a first-class concern. And should the AI remember previous conversations — yes, customers expect continuity, which means conversational memory on top of enterprise knowledge retrieval.

**✅ Functional** — what the platform must do:

- Answer FAQs
- Search enterprise knowledge
- Create and update tickets
- Query CRM
- Process refunds
- Escalate cases
- Maintain conversation history

**⚙️ Non-functional** — the qualities that make it production-grade:

- High availability
- Low latency
- Enterprise security
- High accuracy
- Easy onboarding of new business systems
- Highly scalable
- Cost efficient

## 2 · High-level architecture

**Retrieval, action, and memory as three peers, not a pipeline.**

A customer request comes in through web, mobile, or WhatsApp, passes through the API Gateway and an authentication layer, and reaches an AI Orchestrator Agent. From there it fans out to three capabilities that solve different problems — RAG for retrieval, tool calling for action, memory for continuity — converging through MCP servers into the actual backend systems, before a response comes back through the enterprise LLM and, when needed, a human approval step.

```
Customer
│
Web / Mobile / WhatsApp
│
API Gateway
│
Authentication Layer
│
AI Orchestrator Agent
┌──────────────┼──────────────┐
│              │              │
RAG Layer   Tool Calling    Memory
│              │              │
│         MCP Servers         │
│              │              │
Knowledge    CRM  Ticketing  Order Mgmt
Base         ERP  Payments   Inventory
│
Enterprise LLM
│
Human Approval
│
Customer Response
```

RAG, tool calling, and memory sit side by side as peers the orchestrator draws on — not a sequential pipeline every request has to pass through in order.

---

## 3 · RAG vs. tool calling

**Why have both — can't the LLM just answer everything?**

They're solving different problems. RAG retrieves information; tool calling executes actions. If a customer asks *"What is your refund policy?"*, the AI retrieves the answer from the knowledge base using RAG. But if they say *"Refund my order,"* the AI has to invoke a business system to actually process it — LLMs generate text, they don't update enterprise databases by themselves.

**📚 RAG** — Retrieves accurate, up-to-date answers from documentation, FAQs, and policies rather than depending on model memory that can be stale or simply wrong.

**🔧 Tool calling** — Executes deterministic business operations — creating tickets, querying CRM, updating records, processing refunds — and is reliable and auditable in a way free-text generation isn't.

---

## 4 · Where MCP fits

**One standardized interface over dozens of backend systems.**

An enterprise support platform sits in front of dozens or hundreds of backend systems. Instead of exposing thousands of individual APIs directly to the LLM, MCP servers — a CRM MCP Server, a Ticketing MCP Server, a Payments MCP Server, an Inventory MCP Server — each advertise their available tools, resources, prompts, and capabilities. The AI discovers what's available dynamically instead of hardcoding every integration, and internally an MCP server can still call REST, GraphQL, a database, or a legacy application.

> REST remains the underlying communication mechanism — MCP doesn't replace it. MCP standardizes how AI systems **discover** and **interact with** enterprise capabilities. REST solves communication; MCP solves AI interoperability and discoverability.

## 5 · Multi-agent orchestration

**Not every request needs a planner.**

A simple request like *"Track my order"* is a single tool call — no orchestration needed. But *"My laptop arrived damaged. Refund the order, cancel the warranty, notify shipping, and create a high-priority support ticket"* requires planning and coordination across multiple systems. That's when a Planner Agent earns its cost, decomposing the request across specialist agents.

```
Customer Request
↓
Planner Agent
↓
─────────────────────────────
Knowledge Agent
CRM Agent
Refund Agent
Ticket Agent
Shipping Agent
Notification Agent
─────────────────────────────
↓
Merge Results
↓
Customer Response
```

Each agent specializes in one domain — Knowledge, CRM, Refund, Ticket, Shipping, Notification — improving modularity and maintainability. Results merge back into a single customer response. For straightforward requests, a single agent or direct tool call is faster and cheaper; multi-agent workflows are reserved for complex, cross-system tasks that require planning or parallel execution.

## 6 · Three layers of memory

**Separating conversational memory from enterprise knowledge.**

**⏱️ Short-term memory** — Maintains context during the current session. If a customer asks "Where's my package?" and later "Can you refund it?", the AI understands "it" refers to the same order.

**🗂️ Long-term customer memory** — Persistent preferences and history — preferred language, communication channel, previous purchases, past support interactions — enabling personalized support across sessions.

**📚 Enterprise knowledge** — Stored separately in RAG: product documentation, policies, FAQs, troubleshooting guides. Keeping this apart from conversational memory improves both accuracy and maintainability — a stale customer preference and an outdated policy document fail in very different ways, and conflating them makes both harder to fix.

---

## 7 · Human approval workflow

**Balancing automation with governance.**

Human approval is required for high-risk or high-value actions: refunds above a threshold, VIP customer escalations, account deletion, legal or compliance requests, and changes to payment information.

```
Refund Request
↓
AI Validation
↓
Approval Required?
↓ Yes
Manager Approval Queue
↓
Approved
↓
Execute Refund
```

The AI validates the request first — most requests never reach a human at all. Only the ones that cross a risk or value threshold route into a manager approval queue before execution.

## 8 · Scaling to 50M customers

**10 million conversations a day — what has to scale independently.**

**🧩 1 · Stateless AI services** — API gateways, orchestrators, and LLM routing services stay stateless so they scale horizontally behind load balancers.

**🗄️ 2 · RAG scaling** — Instead of searching all documents, partition embeddings by product, region, language, and business unit to cut retrieval latency.

**⚡ 3 · Semantic cache** — Many customers ask identical questions — "What is your return policy?", "Where is my order?" A semantic cache answers repeated queries without invoking the LLM, cutting both cost and latency.

**🔄 4 · Asynchronous workflows** — Long-running tasks — refunds, warranty cancellations, shipping investigations — run asynchronously. The AI immediately replies "Your request has been submitted," while background workers finish the job.

**🚦 5 · Rate limiting** — Per-user limits, per-tenant quotas, tool invocation limits, and circuit breakers protect backend systems from downstream failures.

**🔒 6 · Security** — Every tool invocation propagates enterprise identity, OAuth tokens, RBAC/ABAC permissions, and audit logs. The LLM never bypasses application authorization — business systems remain the source of truth for access control.

**💰 7 · Cost optimization — model routing** — Not every request needs the largest LLM. Routing by task complexity optimizes cost while preserving quality where it matters: FAQ → small LLM, refund investigation → large reasoning model.

**Global deployment**: regional AI gateways and orchestrators close to users for low latency, knowledge indexes and vector databases partitioned by geography where data residency requires it, stateless AI services running active-active across regions, customer data kept within compliance boundaries, and global load balancing routing traffic to the nearest healthy region.

## 9 · Tradeoffs

**Seven technologies, and what each one costs.**

| Technology | Best use | Advantages | Tradeoffs |
|---|---|---|---|
| RAG | Enterprise knowledge retrieval | Accurate, up-to-date answers | Requires indexing and embedding pipeline |
| Tool Calling | Execute deterministic business actions | Reliable and auditable | Limited to predefined tools |
| MCP | Standardized enterprise integrations | Excellent discoverability and extensibility | Additional abstraction layer |
| Agent Framework | Multi-step workflows | Modular, scalable, parallel execution | More orchestration complexity |
| Human Approval | High-risk operations | Governance and compliance | Increased response time |
| Memory | Personalized conversations | Better customer experience | Requires lifecycle management and privacy controls |
| Semantic Cache | Repeated customer questions | Lower latency and cost | Cache invalidation complexity |

## 11 · Final design summary

**Specialized responsibilities, not one LLM doing everything.**

The architecture separates customer support into specialized responsibilities instead of relying on a single LLM. RAG powers accurate answers by retrieving the latest enterprise knowledge rather than depending on model memory. Tool calling executes deterministic business operations — creating tickets, querying CRM, updating records, processing refunds. MCP servers provide a standardized AI interface to enterprise applications, letting new systems onboard with minimal changes while REST stays the underlying communication mechanism. Agent orchestration coordinates complex workflows spanning multiple business domains. Memory splits into short-term conversational context, long-term customer personalization, and enterprise knowledge managed through RAG. Human approval workflows govern high-risk actions.

Scalability comes from stateless services, horizontally scalable orchestrators, semantic caching, asynchronous processing, partitioned vector databases, and regional deployments. Security comes from enterprise authentication, RBAC/ABAC authorization, identity propagation, encryption, audit logging, and strict tenant isolation. Cost is optimized using semantic caching, model routing, asynchronous execution, and targeted retrieval so expensive LLMs are invoked only when necessary.

> This layered architecture creates a secure, scalable, and maintainable enterprise AI Customer Support Platform where each technology — RAG, MCP, tool calling, agent orchestration, memory, and human approval — is used for the responsibility it's best suited to handle, rather than treated as a competing solution.
