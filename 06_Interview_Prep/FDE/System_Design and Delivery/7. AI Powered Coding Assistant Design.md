# AI Powered Coding Assistant Design

*System Design & Delivery Interviews — Reference*

The interview question: design an AI-powered coding assistant like GitHub Copilot that provides real-time code completion, explains code, generates unit tests, fixes bugs, refactors code, and answers developer questions — integrated seamlessly into the IDE. Explain how **context engineering, semantic retrieval, model routing, semantic caching, and output validation** combine to keep suggestions fast, accurate, and safe.

`<300ms autocomplete` · `millions of developers` · `context-engineered` · `end-to-end architecture`

---

## 1 · Define the problem space

**A GitHub Copilot-style assistant, clarified before it's architected.**

A developer typing inside an IDE should get real-time code completion, multi-line generation, code explanations, generated unit tests and documentation, refactoring, bug fixes, and answers to coding questions — all workspace-aware and under a strict latency budget. That combination of "must feel instant" and "must understand my entire repository" is what makes this a context-engineering problem as much as a distributed-systems one.

> Is the assistant cloud-based or can it run locally — both models exist, and the answer changes where inference happens. Should suggestions be real-time as the user types — yes, which sets the latency budget before anything else is designed. Which IDEs and languages need support — VS Code, IntelliJ, Visual Studio, and most mainstream languages, which argues for a thin, IDE-agnostic extension talking to a shared backend. Should it understand the entire repository or just the current file — the whole repo, within reason, which is exactly why context engineering becomes the hard problem. Do enterprise customers need private models and on-prem deployment — yes, which shapes the security and deployment story from day one.

**✅ Functional** — what the assistant must do:

- Real-time code completion
- Multi-line code generation
- Explain selected code
- Generate unit tests
- Generate documentation / comments
- Refactor code
- Fix compilation / runtime errors
- Answer coding questions
- Search project codebase
- Generate commit messages
- Support multiple languages
- Workspace-aware suggestions

**⚙️ Non-functional** — the qualities that make it production-grade:

- <300ms autocomplete latency
- High accuracy
- Low hallucination rate
- Highly available
- Enterprise security
- Support millions of developers
- Personalized suggestions
- Cost efficient

## 2 · High-level architecture

**Cache first, retrieve only on a miss, route by task complexity.**

A keystroke flows from the IDE extension through authentication and the API gateway to a context builder, which combines fresh context signals with conversation memory. A semantic cache sits immediately in front of the expensive path: on a cache hit, the request skips straight to prompt construction; on a miss, the embedding service, vector database, and code retrieval assemble fresh context. The model router then picks a small fast model or a large reasoning model per task, and every output is validated before it ever reaches the editor.

```
IDE Extension
│
Authentication Service
│
API Gateway / Load Balancer
┌──────────────┴──────────────┐
Context Collection      User Preferences
└──────────────┬──────────────┘         Conversation Memory
               │  ◄──────────────────────────────┘
        Context Builder
               │
        Semantic Cache
        ┌──────┴──────┐
    Cache Hit      Cache Miss
        │              │
        │        Embedding Service
        │              │
        │        Vector Database
        │              │
        │        Relevant Code Retrieval
        └──────┬────────┘
          Prompt Builder
               │
          Model Router
        ┌──────┴──────┐
Small Fast Model   Large Reasoning Model
        └──────┬──────┘
        Output Validation
               │
          IDE Suggestions
```

The semantic cache is the load-bearing latency optimization: it lets the common case — a completion the assistant has effectively seen before — skip embedding, retrieval, and often the large model entirely.

## 3 · Step-by-step request flow

**From keystroke to accepted suggestion.**

1. **⌨️ User types code** — The developer starts typing inside VS Code — e.g. `def calculate_total(items):` — and the IDE extension detects the cursor position.
2. **📥 Context collection** — The extension gathers current function, file, open tabs, imports, repo structure, cursor location, language, recent edits, and compiler errors — selecting only what's relevant rather than sending the whole repository.
3. **🔎 Semantic code search** — The assistant searches for semantically related code — similar functions, existing helpers, internal APIs, coding patterns, project conventions — preventing duplicate implementations and encouraging reuse.
4. **🧱 Prompt construction** — A structured prompt combines system instructions, the user request, current code, retrieved snippets, language/framework, repository conventions, and relevant documentation.
5. **🚦 Model routing** — The request routes to the most appropriate model based on task complexity, balancing latency, quality, and cost.
6. **✨ Generate suggestion** — The selected model generates code completion, explanation, refactoring suggestions, unit tests, documentation, or bug fixes.
7. **🛡️ Output validation** — Before returning: parse generated code, check syntax, validate formatting, apply security filters, detect hallucinated APIs, and remove unsafe patterns. Invalid or low-confidence outputs may be regenerated or suppressed.
8. **📤 Return suggestion** — Suggestions stream back to the IDE and display inline. The developer can accept, partially accept, reject, or request alternatives — valuable feedback for future personalization.

## 4 · Context signals & model routing

**What gets collected, and which model handles which task.**

Not every task needs the largest model, and not every context signal is worth its token cost. The routing decision and the context-collection decision are really the same kind of tradeoff: spend latency and money only where it buys accuracy.

`Current function` `Current file` `Open tabs` `Imported libraries` `Repository structure` `Cursor location` `Programming language` `Recent edits` `Compiler errors` `Git branch (optional)`

| Task | Recommended model |
|---|---|
| Next-word completion | Small, low-latency model |
| Multi-line completion | Medium model |
| Code explanation | Larger reasoning model |
| Bug fixing | Larger reasoning model |
| Refactoring | Larger reasoning model |
| Architecture questions | Most capable reasoning model |

## 6 · AI-specific design considerations

**The concepts interviewers actually want to hear.**

**🧩 Context engineering** — Only include information that materially improves the response — current function, related classes, imports, similar implementations, coding standards, project docs. Avoid sending unnecessary files to reduce latency and token usage.

**🔎 Semantic search** — Instead of keyword matching, use embeddings to retrieve code with similar intent. Searching "calculate tax" may retrieve `compute_gst()` because the underlying semantics are similar.

**📝 Prompt management** — Maintain different prompt templates per task — completion, test generation, bug fixing, refactoring, documentation, explanation. Versioning prompts enables safe experimentation and rollback.

**🚦 Model routing** — Not every task needs the largest model: autocomplete gets a fast model, explaining code gets a medium model, refactoring architecture gets an advanced reasoning model — optimizing cost and responsiveness.

**⚡ Semantic cache** — Frequently requested completions — framework boilerplate, standard algorithms, popular API usage — get cached. Semantic matching allows reuse even when requests are phrased differently.

**🪟 Context window management** — Large repositories can exceed model limits. Retrieve only relevant files, chunk code intelligently, compress long histories, prioritize nearby code over distant files, and remove irrelevant context.

```
Full Repository & Workspace (potentially millions of tokens)
                    │  ✕ unrelated files
Relevant Signals (current file, imports, open tabs, cursor, recent edits)
                    │  ✕ distant history
Compressed & Ranked Context (semantic search + prioritization)
                    │
Final Prompt (fits model context window)
```

Context engineering is a funnel, not a filter that runs once — the repository narrows to signals, signals narrow to ranked context, and only the ranked context becomes the prompt that actually reaches the model.

## 7 · Scaling to millions of developers

**Staying under 300ms while serving everyone.**

**🧩 1 · Stateless API servers** — API servers sit behind load balancers so they scale horizontally with demand.

**🗄️ 2 · Distributed vector databases** — Embeddings are sharded across regions and repositories rather than living in one giant index.

**⚙️ 3 · GPU inference clusters** — Autoscaling GPU clusters absorb bursty demand from IDE keystrokes without over-provisioning at idle.

**📡 4 · Streaming responses** — Tokens stream back as they're generated, so perceived latency drops even when total generation time doesn't.

**🌍 5 · Multi-region deployment** — Inference runs close to developers geographically, and static assets are served from a CDN.

**🚦 6 · Rate limiting & batching** — Request batching where appropriate, plus rate limiting and quota management, protect shared infrastructure from runaway usage.

Rough latency budget for a sub-300ms autocomplete: **~10ms** cache check → **~40ms** context assembly → **~200ms** model inference (streamed) → **~50ms** validation. The cache check and context assembly stay cheap, most of the budget goes to streamed model inference, and validation runs in the remaining margin.

## 8 · Security considerations

**Source code is the most sensitive asset in the pipeline.**

- Never train foundation models on private enterprise code without explicit consent.
- Encrypt source code in transit and at rest.
- Enforce repository-level access controls.
- Respect organizational permissions during retrieval.
- Mask secrets and credentials before sending context.
- Support deployment within a customer's private environment for highly regulated industries.
- Maintain audit logs for compliance and governance.

## 9 · Tradeoffs

**Six decisions, and what each one costs.**

| Decision | Pros | Cons |
|---|---|---|
| Small model | Fast and inexpensive | Lower reasoning quality |
| Large model | Better suggestions | Higher latency and cost |
| Full repository context | Richer understanding | Higher token usage |
| Retrieved context only | Lower cost and faster | May miss relevant information |
| Cloud inference | Easy to scale | Privacy considerations |
| Local inference | Better data privacy | Limited by local hardware |

## 10 · Common follow-up questions

**Three questions interviewers reach for.**

**🔒 How do you avoid leaking customer code?**

- Isolate customer data by tenant.
- Do not use private repositories for public model training unless explicitly permitted.
- Retrieve only documents the user is authorized to access.
- Mask sensitive information before sending prompts.
- Offer private or on-premises deployments for enterprise customers.
- Enforce strict access controls and auditing.

**⚡ How do you reduce latency below 300ms?**

- Use a lightweight model for inline autocomplete.
- Stream tokens as they are generated.
- Maintain persistent connections from the IDE.
- Cache embeddings and frequent completions.
- Perform semantic indexing in the background.
- Deploy inference close to users in multiple regions.
- Limit retrieved context to only what is necessary.
- Use speculative decoding or similar inference optimizations where supported.

**🎯 How do you personalize suggestions?**

- Learn preferred coding style — naming, formatting, patterns.
- Prioritize project-specific APIs and frameworks.
- Incorporate accepted versus rejected suggestions.
- Respect repository coding standards and linting rules.
- Tailor prompts using developer and team preferences while keeping raw source code protected.
- Continuously refine retrieval based on feedback and recent activity.

## 11 · Final design summary

**A retrieval-augmented, context-engineered system — not one call to a big model.**

The strongest answers treat a coding assistant as a retrieval-augmented, context-engineered system rather than a single call to a large LLM: gathering and prioritizing relevant context instead of sending entire repositories, using semantic retrieval and embeddings to improve suggestions, routing across models to balance latency, cost, and quality, and managing context windows carefully for large codebases.

Scalability comes from stateless API servers, distributed vector databases, autoscaling GPU inference, streaming responses, and multi-region deployment. Security comes from tenant isolation, repository-level access control, secret masking, and — for regulated industries — private or on-premises deployment. Enterprise concerns like security, privacy, and access control aren't an afterthought; they shape the architecture from the first clarifying question onward.

> This layered architecture treats context engineering, semantic retrieval, model routing, semantic caching, and output validation as complementary techniques — each earning its place by trading latency, cost, and quality against the others, rather than any one of them being "the" solution.
