Four retrieval metrics, and they disagree on purpose.

Precision, Recall, MRR and nDCG all score the same ranked list and all move differently as you change K. Drag K and watch which ones react — that divergence is the whole reason you report four numbers instead of one.

These are the classic set-overlap definitions — a chunk is relevant or not, checked against a fixed ground-truth set, no LLM involved. Tutorial 02's "Contextual Precision/Recall" reuse these names for a different, LLM-judged computation (rank-weighted precision, coverage-of-expected-output recall) — see 02-llm-judged-retrieval-metrics.html.

Which metric answers which question

MetricQuestionBlind toReach for it when
Precision@KOf the K retrieved, how many are relevant?Relevant chunks that were never retrievedContext windows are expensive and noise is diluting the prompt
Recall@KOf all relevant chunks, how many did we find?Where in the ranking they landedAnything downstream is capped by this — check it first
MRRHow early does the first relevant chunk appear?Everything after the first hitOne best chunk exists and position matters

The whole implementation — no LLM, no API key, no cost

def precision_at_k(retrieved, relevant, k):
    top_k = retrieved[:k]
    return len([d for d in top_k if d in relevant]) / k

def recall_at_k(retrieved, relevant, k):
    top_k = retrieved[:k]
    return len([d for d in top_k if d in relevant]) / len(relevant)

def mrr(retrieved, relevant):
    for rank, doc in enumerate(retrieved, start=1):
        if doc in relevant: return 1.0 / rank
    return 0.0

def ndcg_at_k(retrieved, grades, k):
    dcg  = sum(grades.get(d, 0) / math.log2(i + 2) for i, d in enumerate(retrieved[:k]))
    # the ideal ranking includes chunk_5 (grade 3) — which is why nDCG
    # stays capped at 0.51 no matter how you reorder what WAS retrieved
    ideal = sorted(grades.values(), reverse=True)[:k]
    idcg = sum(rel / math.log2(i + 2) for i, rel in enumerate(ideal))
    return dcg / idcg if idcg > 0 else 0.0
