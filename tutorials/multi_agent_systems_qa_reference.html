01

How Subagents Communicate & State Transfers

Core communication patterns

  • Message passing — agents exchange structured messages through a shared bus, queue, or direct calls, each carrying sender, content, and intent.
  • Shared state / blackboard — agents read/write to one common state object (e.g., LangGraph's StateGraph); no direct agent-to-agent messages.
  • Orchestrator-mediated — a central supervisor routes tasks and passes only relevant context to each subagent.
  • Hierarchical / handoff — one agent explicitly hands off control to another, passing a task description and a relevant state slice.

How state gets transferred

  • Full state passing — the whole state object flows through every agent; simple but can bloat context.
  • Selective/filtered state — only the fields a subagent needs are extracted and sent onward.
  • Message history append — each agent's output is appended to a running message list (LangGraph's MessagesState).
  • Scratchpad / external store — long-term memory lives in a vector/KV store; short-term state stays in-context.

Common architectures

PatternCommunication styleState handling
Supervisor-WorkerOrchestrator routes, workers report backSupervisor holds master state, workers get slices
Peer-to-PeerAgents message each other directlyLocal state per agent, synced via messages
Sequential PipelineOutput of A is input to BState transforms at each stage
Graph-based (LangGraph)Edges define control flowShared state schema, updated via reducers

Key design tensions: context window pressure (full state gets expensive at scale), failure isolation (peer-to-peer is harder to trace than orchestrator patterns), and determinism vs. flexibility (explicit graph edges are predictable; free-form agent chat is flexible but less controllable).

Most Common Agent Design Patterns

Foundational patterns

  • ReAct — alternates between reasoning and acting, observing tool results before deciding the next step.
  • Reflection — generates output, then critiques and revises its own work (or a separate critic does).
  • Planning — decomposes a complex goal into subtasks before executing.

Routing & control flow patterns

  • Routing — a classifier picks which predefined path/tool/subagent handles the input.
  • Prompt chaining — output of one call feeds directly into the next, as a fixed pipeline.
  • Parallelization — multiple calls run at once on different subtasks/perspectives, then get aggregated.

Multi-agent coordination patterns

  • Orchestrator-Workers — dynamically decomposes a task at runtime, delegates to generic workers, synthesizes results.
  • Multi-Agent (Supervisor) — specialized agents collaborate, each owning a fixed domain.
  • Evaluator-Optimizer — a generator and an evaluator loop until the output passes a rubric.

Orchestrator-Workers vs. Multi-Agent — Core Distinction

  • Orchestrator-Workers — one central brain decides how to break down the task at runtime, dispatching to interchangeable, stateless workers with no distinct identity.
  • Multi-Agent (Supervisor) — agents have a fixed specialization decided in advance; the supervisor routes to the right specialist rather than inventing a decomposition.
AspectOrchestrator-WorkersMulti-Agent (Supervisor)
DecompositionDynamic, at runtimeFixed roles at design time
Worker identityGeneric, interchangeableSpecialized, distinct tools
FlexibilityHigh — unpredictable shapesLower — known categories only
Worker awareness of peersNoneOften yes, via shared state
Misuse failure modeOverkill for simple tasksRigid if task fits no specialist

When to use which: orchestrator-workers when the number/shape of subtasks isn't known ahead of time; multi-agent supervisor when domains are known and each agent should develop deep, tool-specific competence. They compose — a supervisor specialist can internally run orchestrator-workers itself.

04

How Messages Are Actually Communicated

Orchestrator-workers

  • No worker-to-worker communication — workers only ever talk to the orchestrator.
  • Task-scoped payload, not full history — each worker gets a narrow, self-contained instruction.
  • Sync or async collection — orchestrator dispatches N calls, waits, then aggregates.
  • Stateless — every worker call is a fresh context window.
# Pseudocode: orchestrator-workers
subtasks = orchestrator.plan(task)          # decompose
results = [worker.run(t) for t in subtasks] # isolated calls
final = orchestrator.synthesize(results)    # merge

Multi-agent supervisor

  • Shared state flows through every agent — typically a MessagesState that every agent reads and appends to.
  • Agents see prior turns — the next agent can see what the previous one already said.
  • Structured handoff, not raw chat — supervisor injects a directed instruction alongside the shared history.
  • Centralized (hub-and-spoke, always through supervisor) or decentralized (direct agent-to-agent handoff, e.g. LangGraph's Command(goto=...)).
# Pseudocode: multi-agent supervisor (LangGraph-style)
state["messages"].append(supervisor_instruction)
state = coder_agent.invoke(state)      # appends its own message
state = supervisor.route(state)        # decides next agent
state = sql_agent.invoke(state)        # sees coder's prior message

What's passedNarrow task sliceFull/shared message history
Agents see each otherNoOften yes, via shared state
Message formatAd-hoc input/output pairsStructured message list
CouplingLoose — stateless workersTighter — built on shared context
Failure visibilityEasy — isolated failuresHarder — shared history grows

The Nuance — Do Both Really Go Through a Hub?

Yes — both are hub-and-spoke; neither has a direct worker/agent-to-agent wire. The real difference is what the hub does with a message as it passes through.

    end
  • Orchestrator-workers — the orchestrator is a translator/re-packager. If Worker A's output needs to reach Worker B, the orchestrator must manually extract, interpret, and re-inject it as a new task. Nothing flows automatically.
  • Multi-agent supervisor — the supervisor is a pass-through router. Shared state flows automatically to whoever is routed to next — no reformatting needed.
Orchestrator-WorkersMulti-Agent Supervisor
Info passes through hub?YesYes
Automatic or manual?Manual — hub reconstructs contextAutomatic — shared state carries forward
Next node sees raw prior output?No — only what hub forwardsYes — raw turn is in shared state
Typical roundsUsually one fan-out/fan-inMany rounds, evolving conversation

The simplest framing: it's not "communicate through the hub vs. don't" — it's whether the hub has to do work to share context, or whether context shares itself. (Some real orchestrator-worker systems give workers a shared scratchpad to reduce this manual burden — at which point the two patterns genuinely blur.)

Routing & Control Flow Patterns

Routing

A classifier examines input and picks one of several predefined paths — paths are fixed; only which one gets picked is dynamic.

  1. Input received.
  2. Classification call reasons which category the input falls into.
  3. Route selection maps to one of N predefined branches.
  4. Branch execution — the selected branch's fixed pipeline runs.
  5. Response returned — no cross-branch synthesis.

Use case — support email auto-router: incoming emails classified into billing / bug-report / feature-request, each forwarded to a category-tuned template. Branches never talk to each other.

Prompt Chaining

Output of step N becomes input of step N+1 in a fixed, linear sequence — no branching, no dynamic decision.

  1. Step 1 transforms the raw input.
  2. Optional gate check validates output before continuing.
  3. Step 2 takes step 1's output verbatim.
  4. Repeat through steps 3...N, each strictly dependent on the previous.
  5. Final output returned.

Use case — blog post pipeline: outline → full prose → grammar/style pass → SEO metadata. Each step sees only the previous step's output; sequence never changes.

Parallelization

The same task runs multiple times simultaneously (sectioning or voting), then results are aggregated.

  1. Fan-out — task split into fixed, predetermined parallel calls.
  2. Concurrent execution — all calls run independently at once.
  3. Fan-in — results collected once every call returns.
  4. Aggregation — merge via majority vote or LLM synthesis.
  5. Final output returned.

Use case — content moderation voting: a flagged post sent to 3 identical moderation prompts at once; 2-of-3 flags trigger removal — a fixed voting rule aggregates 3 parallel, identical-role calls.

07

Workflow vs. Agent, Clarified

Short answer: yes — and it goes further than routing/chaining/parallelization.

  • Routing, prompt chaining, and parallelization are workflows, not agents — the control flow is fixed by the developer in code; the LLM only fills content into fixed slots.
  • Per Anthropic's own taxonomy ("Building Effective Agents"), Orchestrator-Workers and Evaluator-Optimizer are also classified as workflows — even with one dynamic decision point each.
  • What earns the strict "agent" label is an open-ended loop where the LLM decides the entire trajectory — how many steps, which tools, in what order, and when to stop — with no predetermined path.
  • Multi-Agent Supervisor gets closest, since routing can continue indefinitely and the supervisor decides termination — but even it routes within a fixed set of specialists.

Rule of thumb: it's a workflow if you could draw its full possible control-flow diagram on a whiteboard before running it once. It's an agent if the diagram would differ every run because the model is inventing the path as it goes.

Ties back to LangChain vs. LangGraph: this isn't about which library is used — LangGraph can build a strict workflow too (a fixed graph, no cycles). It's about whether the model or the code decides the trajectory and its stopping point.
