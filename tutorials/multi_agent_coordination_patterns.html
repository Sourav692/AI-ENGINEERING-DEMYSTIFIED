Multi-Agent Coordination Patterns

Step-by-step internal execution flow for the three core coordination patterns, each paired with a production-style use case showing exactly how the agents communicate and hand off work.

01

Orchestrator-Workers

runtime decomposition

A single orchestrator inspects the task and decides at runtime how many subtasks it needs and what each one is, dispatching them to generic, disposable worker agents that share no context with one another.

Step-by-step execution flow

  1. Task ingestion — orchestrator receives the raw request as a single payload.
  2. Task analysis — an LLM call reasons about the task's internal structure and whether it decomposes into independent parts.
  3. Dynamic decomposition — orchestrator emits a structured plan: a list of subtasks with scoped inputs. The count is decided here, not hardcoded.
  4. Worker dispatch — subtasks go out in parallel (independent work) or sequentially (dependent chain).
  5. Isolated execution — each worker gets only its own task-scoped payload — no shared history, no visibility into other workers.
  6. Result collection — orchestrator waits for all dispatched workers to return.
  7. Synthesis — orchestrator merges outputs, resolving conflicts and reconciling formatting.
  8. Quality gate (optional) — re-check merged output against the original brief; re-dispatch workers for any gaps.
  9. Final response — synthesized output returned to the caller.

Real-time use case — enterprise codebase migration assistant

Scenario: An engineering team asks the system: "Migrate our 40-file Java payment module to Kotlin, preserving all existing test coverage."

  1. Static analysis pass — the orchestrator walks the file tree and maps dependencies between files before deciding anything.
  2. Runtime clustering — it groups the 40 files into 3 clusters by dependency locality (core domain models, gateway adapters, test fixtures). A differently-shaped codebase would produce a different number of clusters — this isn't a fixed rule.
  3. Parallel dispatch — 3 workers are spun up, each given only its cluster's files and the target style guide — nothing about the other clusters.
  4. Independent ReAct loops — each worker runs: read file → propose Kotlin translation → run compiler check → fix errors → run unit tests → return diff.
  5. Conflict detection — because workers share no context, Worker 1 doesn't know Worker 2 renamed a shared interface. The orchestrator catches this mismatch during collection.
  6. Targeted follow-up — rather than redoing everything, the orchestrator issues one narrow follow-up task to Worker 2 alone to fix just the interface mismatch.
  7. Final assembly — one pull request is composed with a synthesized summary: files changed, test pass rate, flagged manual-review items.
  8. Why this pattern fits: the number of logical migration clusters can't be known until the repo is actually inspected — a fixed pipeline would over- or under-decompose the work.
02

Multi-Agent Supervisor

fixed specialist roles

Specialist agents exist with roles fixed at design time. A supervisor's only job is to route — not invent task structure — and every agent reads from and writes to one shared state object.

Step-by-step execution flow

  1. Input received — supervisor gets the incoming message, appended to shared state.
  2. Intent classification — an LLM call reasons: which specialist domain does this belong to?
  3. Routing decision — supervisor emits a structured decision, e.g. route: "billing_agent".
  4. Handoff — control and the full shared message history pass to the selected specialist.
  5. Specialist execution — the specialist runs its own tool-calling loop with domain-restricted tools.
  6. State update — the specialist appends its findings directly to the shared state, visible to any agent that reads next.
  7. Return to supervisor — control returns; supervisor checks whether the task is fully resolved.
  8. Re-routing (if needed) — supervisor may hand off to a second specialist, which now sees the first specialist's turn in shared history.
  9. Termination check — supervisor decides the task is resolved and returns the final response.

Real-time use case — customer support ticket resolution

Scenario: A SaaS support inbox routes messages through a system with three specialists: Billing Agent, Technical Agent, Refund Agent.

  1. Ticket arrives — "I was charged twice this month and my dashboard won't load" — appended as the first shared-state entry.
  2. Multi-issue detection — the supervisor recognizes two distinct issues bundled together and decides to sequence them, billing first.
  3. Scoped handoff — routes to the Billing Agent with the full shared state. This agent's tools are restricted to the payments system only — no ticketing or code access.
  4. Finding written to shared state — Billing Agent confirms a duplicate charge and appends the raw finding into the visible message history — not a private summary back to the supervisor.
  5. Re-evaluation — supervisor re-reads the updated state and decides a refund is owed — routes onward.
  6. Downstream reuse of context — the Refund Agent reads the same shared state, including the billing finding, and issues the refund without re-deriving it independently.
  7. Second routing thread — separately, the dashboard issue routes to the Technical Agent, which has log-query tools instead of payment tools.
  8. Unified reply — once both threads resolve, the supervisor composes one customer-facing response covering both issues.
  9. Why this pattern fits: the three domains are known in advance and benefit from deep specialization with restricted tool access — a dynamic orchestrator has no advantage since the roles never change shape.
03

Evaluator-Optimizer

generate → judge → refine

A generator produces a candidate; an evaluator scores it against explicit criteria and returns structured feedback. The generator revises against that feedback — looping until it passes or hits a cap.

Step-by-step execution flow

  1. Initial generation — generator produces a first draft from the task brief.
  2. Evaluation — evaluator scores the draft against a rubric, returning structured pass/fail plus specific issues.
  3. Branch check — pass → skip to finalization; fail → continue.
  4. Feedback-conditioned regeneration — generator receives its own draft plus the specific critique, and revises only what was flagged.
  5. Loop — return to evaluation with the new draft; repeat until pass or iteration cap.
  6. Finalization — the passing (or best-scoring) draft is returned, often with the evaluator's approval rationale attached.

Internal working — sequence diagram

sequenceDiagram
    participant U as User
    participant G as Generator
    participant E as Evaluator

    U->>G: "Write ad copy for product launch"
    G->>E: Draft v1
    E->>E: Score against brand rubric
    E-->>G: FAIL - tone too casual, missing CTA
    G->>G: Revise using specific critique
    G->>E: Draft v2
    E->>E: Re-score
    E-->>G: FAIL - CTA present, missing legal disclaimer
    G->>G: Revise again
    G->>E: Draft v3
    E->>E: Re-score
    E-->>G: PASS
    G->>U: Final approved copy

Real-time use case — brand-compliant marketing copy generation

Scenario: A marketing team needs a product launch announcement that must pass a strict brand voice guide and legal disclaimer requirements.

  1. First draft — the generator produces punchy, casual copy with a strong hook, from the raw brief.
  2. Rubric-based scoring — the evaluator, holding the brand rubric as its system context, finds two violations: tone too casual, no call-to-action.
  3. Structured critique — feedback isn't just "fail" — it returns exact line references and the rule violated, e.g. {issue: "opening line uses slang", rule: "brand-voice-3.2"}.
  4. Targeted revision — the generator receives its own draft plus this critique and revises only the flagged lines, not a full rewrite.
  5. Second pass, new issue found — tone and CTA now pass, but the evaluator catches a missing legal disclaimer for pricing changes.
  6. Third revision — generator inserts the disclaimer boilerplate while preserving the already-approved tone and CTA.
  7. Approval — evaluator scores v3 and returns pass; copy is released.
  8. Why this pattern fits: the task has an objective, checkable rubric that a second reasoning pass verifies better than the generator can self-check in one shot — separating "produce" from "judge" catches issues a single agent tends to miss scoring its own work.
