1.1The precision/context split — why this pattern exists

▸

What it is

Standard RAG has one dial that fights itself: chunk size. Small chunks make similarity search precise but starve the LLM of context. Large chunks give the LLM context but blur the embedding, so search gets imprecise. Parent document retrieval breaks that coupling.

How it works

Split every source document into small child chunks and embed only those. Each child keeps a reference to its parent — the whole document, or a medium chunk containing it. Search over child vectors (sharp hits), then swap each hit for its parent before it reaches the LLM (full context). This is the "small-to-big" pattern.

Code — Parent_Document_Retrieval.ipynb

child_splitter = RecursiveCharacterTextSplitter(chunk_size=400)
vectorstore = Chroma(collection_name="full_documents",
                      embedding_function=OpenAIEmbeddings())
store = InMemoryStore()                # docstore: parent_id -> full Document

full_doc_retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,           # only ever holds CHILD chunk vectors
    docstore=store,                    # holds the PARENT documents
    child_splitter=child_splitter,
)
full_doc_retriever.add_documents(docs) # splits, embeds children, stores parents

In your notebooks

Parent_Document_Retrieval.ipynb, cells 12–20 — a raw child hit is printed short; the retriever's own output for the same query is printed long.

"Parent document retrieval decouples the retrieval unit from the generation unit — index small child chunks for precise search, but return the parent so the LLM gets full context. It's a two-tier store: a vector store for children, a docstore for parents, joined by an id."

1.2Child-only mode — the parent is the whole document

▸

What it is

The simplest config: no parent_splitter, only a child_splitter. The "parent" is the entire original Document — unbounded size.

How it works

add_documents() splits each source into children, embeds them, and stores the whole source in the docstore keyed by an id every child carries in metadata. At query time, similarity search returns children, then a deduplicated mget fetches the unique parents behind the top hits.

Code — Parent_Document_Retrieval.ipynb, cells 18-20

full_doc_retriever.add_documents(docs)
print(list(store.yield_keys()))          # parent ids now in the docstore

sub_docs = vectorstore.similarity_search("What is LangSmith?", k=2)
print(len(sub_docs[0].page_content))     # short — a 400-char child

retrieved_docs = full_doc_retriever.invoke("What is LangSmith?")
print(len(retrieved_docs[0].page_content)) # long — the entire source doc
"In child-only mode the parent has no size limit, so large source files can blow your context window — that's exactly why the two-splitter mode exists."

1.3Two-splitter mode — bounding the parent size

▸

What it is

The production-shaped config: a child_splitter (small, ~400 chars) and a parent_splitter (medium, ~2000 chars). The parent is no longer the whole document — it's a bounded chunk.

How it works

add_documents() runs parent_splitter first, storing each medium chunk in the docstore, then runs child_splitter on every parent chunk to make the searchable children. This caps prompt size per retrieved hit while still carrying real context.

Code — Parent_Document_Retrieval.ipynb §3

parent_splitter = RecursiveCharacterTextSplitter(chunk_size=2000)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=400)

big_chunks_retriever = ParentDocumentRetriever(
    vectorstore=vectorstore, docstore=store,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,   # <- the only new argument
)
big_chunks_retriever.add_documents(docs)
print(len(list(store.yield_keys())))   # many parent ids, not one per file
"Two-splitter mode is what you'd actually run in production — unbounded 'parent = whole document' risks the context window; capping the parent gives real context without an unbounded prompt."

1.4The docstore — a key-value store, never embedded

▸

What it is

A plain id → Document store holding parent content. Parents are never embedded or searched — only fetched by id after a child wins similarity search.

How it works

ParentDocumentRetriever calls docstore.mset(...) on index and docstore.mget([...]) on query. InMemoryStore is a Python dict — fast, gone on restart. BaseStore is the interface; swapping backends means implementing four methods.

Code — 08_BetterRetriever.ipynb, cell 8

from langchain_core.stores import BaseStore

class PostgresStore(BaseStore[str, DocumentModel]):
    def mget(self, keys): ...      # fetch parents by id, batched
    def mset(self, key_value_pairs): ...  # write parents, batched
    def mdelete(self, keys): ...   # remove parents by id
    def yield_keys(self): ...      # iterate all ids
"The docstore is a separate concern from the vector index — a dumb key-value store. That's why you can put the index behind Chroma or PGVector while independently choosing where parents live."

1.5Chroma (in-memory) vs. PGVector — persistence is a choice

▸

What it is

Chroma, as used in the first notebook, defaults to an ephemeral in-memory collection. PGVector, used in the second, stores vectors in a real Postgres table so the index survives restarts.

How it works

Both implement the same VectorStore interface, so ParentDocumentRetriever doesn't care which it holds — the swap is a one-line constructor change. What changes operationally: PGVector needs a running Postgres with pgvector, connection pooling, and index tuning (IVFFlat/HNSW).

Code — 08_BetterRetriever.ipynb, cell 9

from langchain_postgres import PGVector

DATABASE_URL = "postgresql+psycopg://admin:admin@localhost:5432/vectordb"
store = PGVector(
    collection_name="vectordb",
    connection=DATABASE_URL,
    embeddings=OpenAIEmbeddings(),
)  # ParentDocumentRetriever takes `store` here exactly where Chroma was
"The vector store and docstore are two independent persistence decisions. Chroma-in-memory plus InMemoryStore is a demo config — swap either for a persistent backend without touching the retriever's logic."

1.6Wiring into a chain — RetrievalQA

▸

What it is

ParentDocumentRetriever implements LangChain's standard Retriever interface, so it plugs into any chain expecting one.

How it works

chain_type="stuff" concatenates every retrieved document's text directly into the prompt. Because the retriever already swapped children for parents, the LLM sees full parent-sized context, not fragments.

Code — Parent_Document_Retrieval.ipynb, cell 27

qa = RetrievalQA.from_chain_type(
    llm=OpenAI(),
    chain_type="stuff",              # concatenate everything into one prompt
    retriever=big_chunks_retriever,  # any Retriever works here
)
response = qa.invoke("What is LangSmith?")
"chain_type='stuff' is the naive strategy — fine for a couple of parent chunks, but with a large k or big parents you're one query away from blowing the context window."

Mock system design

A real-time customer-support agent over a growing knowledge base.

The prompt

"Design a support agent that answers customer questions by retrieving from a knowledge base of ~5,000 internal articles, growing by ~20 new/edited articles per day. Answers need to include enough context to be trustworthy, p95 latency under 2 seconds, and the system must not degrade as the knowledge base grows to 50,000 articles over the next year."

Latency budget at p95 — ≤ 2s total
flowchart LR
  A["Embed query\n~100-150ms"] --> B["Vector search\n(HNSW)\n~50-100ms"]
  B --> C["Docstore mget\n~20-50ms"]
  C --> D["LLM generation\n~1.5s budget"]

Scoring rubric

  • Chooses parent document retrieval (or justifies not needing it) and states the precision/context tradeoff
  • Specifies concrete child/parent chunk sizes tied to the embedding model and LLM context budget
  • Picks a persistent vector store + docstore — not InMemoryStore / in-memory Chroma
  • Handles incremental ingestion (20/day) with idempotent, content-derived ids — not a full nightly reindex
  • Breaks the latency budget down by stage, summing under 2s at p95
  • Names how retrieval quality is measured before/after any change — an eval set, not vibes
  • Handles zero/low-confidence hits without letting the LLM hallucinate ungrounded
  • Addresses scaling from 5k to 50k articles — index type, whether the docstore choice still holds
→
Reveal a worked strong answer
I'd use ParentDocumentRetriever with a child_splitter around 300–400 characters — precise matches against typical support-question phrasing — and a parent_splitter around 1500–2000 characters, bounding worst-case prompt size even for long articles. Vector store: PGVector, since we're already on Postgres for the docstore and I'd rather run one database than two; add an HNSW index once past a few thousand vectors. Docstore: a Postgres table keyed by a hash of article-id + last-modified timestamp, so the daily ingestion of ~20 changed articles msets idempotently — reruns overwrite, they don't duplicate.

Latency budget at p95 ≤ 2s: query embedding ~100–150ms, HNSW vector search ~50–100ms even at 50k vectors, docstore mget ~20–50ms, leaving ~1.5s for generation — the dominant cost, where I'd stream the response so perceived latency drops even if total time doesn't.

For trust: cap k at 3–4 parents, and if the top similarity score is below a threshold, return "I don't have a confident answer" instead of forcing a generation. I'd build a 50–100 question eval set from real support tickets before launch, track recall@k weekly as the corpus grows, and only re-tune chunk sizes in response to eval regressions, not guesses.
