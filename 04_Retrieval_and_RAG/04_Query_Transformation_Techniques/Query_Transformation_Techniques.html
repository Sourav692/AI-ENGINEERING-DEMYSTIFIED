Query Transformation Techniques

A raw user question is often a bad search query — ambiguous, oddly worded, or several questions stitched into one. These eight techniques rewrite, expand, decompose, or route the query before it ever hits the vector store, so retrieval comes back with something worth generating from.

Naive RAG embeds the user's question as-is and searches with it verbatim. That works fine when the question happens to be phrased close to how the answer is written — and falls apart the moment it isn't. Every technique below intervenes on the query, before or as part of retrieval, without touching how the index itself was built (that's the neighboring concern of 03_Indexing_Techniques/) or how the answer is generated.

They fall into three families, by what they do to the query: turn it into a better one (rewriting & expansion), split it into smaller ones (decomposition), or send it to a different destination entirely (routing).

01

Rewriting & Expansion

Turn one query into a better one — or several — before searching, so the retriever isn't betting everything on the user's exact original phrasing.

Multi-Query

Multi_Query.ipynb
LLM generation call
query→ LLM: 3–5 rephrasings→ search each→ union of hits

An LLM rewrites the question into several differently-worded versions; each is searched independently and the retrieved documents are unioned. Different phrasings surface different relevant chunks that one wording alone would miss.

Use when queries are short or ambiguous and your corpus uses varied terminology for the same concept.

RAG-Fusion

RAG_Fusion.ipynb
LLM generation call
query→ LLM: query variants→ search each→ reciprocal rank fusion

Same fan-out as Multi-Query, but the ranked hit lists are merged with Reciprocal Rank Fusion instead of a flat union — documents that rank well across multiple rewritten queries rise to the top.

Use when you want Multi-Query's recall, plus a principled way to re-rank across the variations rather than a flat union.

Step-Back Prompting

Step_Back_Prompting.ipynb
LLM generation call
query→ LLM: broader "step-back" Q→ retrieve both→ answer

The LLM first asks a more general, principle-level question, retrieves context for that, and answers the original question using both the specific and the broader context together.

Use when a question needs background or underlying-mechanism context that its specific phrasing alone wouldn't retrieve.

HyDE

HyDE.ipynb
LLM generation call
query→ LLM: hypothetical answer→ embed the answer→ search with it

Rather than embedding the question, an LLM drafts a hypothetical answer document and that gets embedded instead. A well-formed hypothetical answer sits closer, in embedding space, to real answer documents than a short question ever does.

Use when the query is short and question-shaped but source documents are long, answer-shaped prose — the vocabulary gap hurts naive retrieval.

02

Decomposition

Split one compound question into simpler sub-questions, retrieve and answer each on its own, then merge the sub-answers into a final answer.

Decomposition

Decomposition.ipynb
LLM generation call (× N sub-questions)
query→ LLM: split into sub-Qs→ retrieve + answer each→ merge → final answer

Breaks a multi-part question into simpler sub-questions, retrieves and answers each independently, then feeds the sub-answers back to the LLM to synthesize the final answer to the original question.

Use when users ask compound or multi-hop questions ("compare X and Y and explain why Z follows") that no single retrieval pass can satisfy.

03

Routing

Send the query to the right retriever, prompt, or filtered index — instead of always querying the same one.

Self-Querying Retrieval

Self_Querying_Retrieval.ipynb
LLM generation call
query→ LLM: parse into filter + text→ metadata filter→ semantic search

An LLM splits the natural-language query into a structured metadata filter (e.g. genre = "sci-fi", year < 2000) plus the remaining semantic text, then applies both the filter and the vector search together.

Use when documents carry rich, filterable metadata and users phrase filter conditions in plain language rather than a facet UI.

Routing — LLM Classifier

Routing_LLM_Classifier.ipynb
LLM generation call
query→ LLM classifies domain→ route to matching prompt

An LLM reads the query and classifies which domain/prompt/chain it belongs to (e.g. "physics" vs. "math"), then dispatches to that route's dedicated retriever or prompt.

Use when you have several distinct domains or data sources and need genuine judgment, not just similarity, to disambiguate between them.

Semantic Routing

Semantic_Routing.ipynb
Embedding-only, no LLM call
query→ embed query + route descriptions→ pick nearest route

Same routing goal as the LLM classifier, but decided by cosine similarity between the query's embedding and each candidate route's description embedding — no generation call in the decision path.

Use when routing needs to be cheap and fast, and the candidate routes are well-separated in embedding space.
