Section 6 — mock system design

Real-time customer support agent, travel booking

The prompt, as an interviewer would give it

"Design an AI agent for a travel booking company's customer support. Customers ask about existing bookings, request cancellations/changes, and ask general policy questions. The system must handle spikes during weather disruptions (thousands of concurrent conversations), never lose a conversation mid-flight, and must not let the agent process a refund without a human checking anything over $200. You have 45 minutes — whiteboard the architecture."

Scoring rubric — what a strong answer covers

  • Topology choice with justification (least autonomous shape that works)
  • Explicit approval gate — where it fires, and how the run resumes without double-processing
  • Memory design — thread-scoped vs. cross-session, on a durable backend
  • Termination and loop guards named explicitly
  • Failure handling at the tool layer, not left to the model
  • Concurrency & streaming story for real-time scale
  • What gets traced, and how a bad run gets debugged after the fact
  • States where it would not use an agent at all

Topology. A supervisor routes to three specialists: booking_lookup (read-only), policy_qa (RAG, no side effects), change_or_cancel (the only agent with write access). Not a swarm — every routing decision needs to be logged through one place for audit, since refunds are involved.

Approval gate. change_or_cancel computes the refund amount as pure logic, and if it's over $200, raises a NodeInterrupt before calling the refund tool. The refund tool itself is idempotent (keyed by booking ID + a generated request ID), so an approved resume can't double-refund.

Memory. PostgresSaver checkpointer, one thread per conversation — durable across restarts and shared across app instances. Cross-session customer memory lives in a separate PostgresStore keyed by customer ID, read once at thread start.

Termination. Hard cap of 15 steps per conversation before forced resolution or human handoff, plus a per-conversation cost ceiling that's logged and alerted on.

Failure handling. RetryPolicy on the booking-system API calls specifically, not on LLM calls; a malformed tool call routes back through the supervisor for a re-plan rather than a blind retry.

Scale. Each conversation is an independent thread — horizontally scalable since state lives in Postgres, not process memory. stream_mode="messages" so customers see incremental responses during a disruption spike.

Observability. Every tool/LLM call is a traced span; alert on span error rate per tool and on interrupt-approval wait time — a backlog of pending refund approvals during a disruption is itself an incident.

Where I wouldn't use an agent. "What's your baggage allowance" is a direct RAG lookup wired as a workflow, not routed through the supervisor's decision-making.
