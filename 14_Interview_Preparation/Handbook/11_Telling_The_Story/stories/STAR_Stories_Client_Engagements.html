SSituation

AIA's business users — actuaries, claims managers, analysts — needed natural-language answers over governed enterprise data spanning multiple business units and markets. There was no self-serve path: an ad-hoc question took 2–10 business days routed through the BI/analyst queue, and a new dashboard took roughly 4 weeks end to end (business question → queue → SQL/ML coding → dashboard build → review → delivery).

TTask

I led this engagement end to end as the field engineer on the account — architecture, hands-on build, and delivery — owning a governed, production-grade MVP that let business users self-serve accurate, explainable answers, with full traceability and governance, inside an 8–9 week advisory-plus-build engagement. The scope was bounded to governed data domains, not open-ended enterprise search.

AAction

I led this engagement end to end — architecture, build, and delivery. I started with a single "do-everything" agent carrying the full prompt, 20+ tools, and conversation history, and it broke down fast in real testing: context bloat degraded accuracy, and the agent kept picking the wrong tool because nothing was specialized by domain.

The pivot happened live, mid-engagement. I re-architected to a Supervisor pattern: an 8-node LangGraph state machine (classify_intent → clarify_or_disambiguate → resolve_assets → route_to_{genie|multi_tool|analysis|visualization} → compose_answer) that interprets intent with a confidence score, asks a clarifying question when confidence drops below 60%, then routes to one of four specialist workers — a Genie agent for text-to-SQL BI questions, a Multi-Tool agent combining LLM-generated SQL with RAG over policy documents, a Data Analysis agent doing z-score anomaly detection and trend stats, and a Visualization agent that creates real AI/BI dashboards via the Lakeview REST API and hands back a clickable link. I built and owned a Context Index — 16 indexed assets (Genie Spaces, metric views, tables, document indexes) — as a semantic-discovery tool the Supervisor calls once per question, with endorsed assets prioritized in routing, so every worker agent sees a consistent, governed set of assets instead of each one searching independently.

I built the Unity Catalog data foundation underneath it myself: bronze tables (products, agents, customers, policies, claims, policy documents), silver enrichment joins (enriched_claims, enriched_policies, customer_360), and seven governed gold-layer metric views (claims, policy performance, agent productivity, fraud analysis) that the agents queried instead of touching raw tables. Short-term memory ran on Delta-backed LangGraph checkpoints keyed by thread_id for multi-turn conversations; prompts lived in a Delta table (ai_ops.agent_instructions) with base + overlay prompts and a 5-minute cache, so I could tune agent behavior without redeploying. I instrumented every node with MLflow tracing (@mlflow.trace, proper span types) and put an AI Gateway in front of the serving endpoint for rate limiting, PII filtering, and guardrails.

Second pivot, further into the build: as the number of specialist domains grew, I evolved the architecture again into a Deep Agent pattern I named Synaptic Command — a central orchestrator that delegates to fully self-contained subagents, each with its own prompt, its own small toolset, and its own context window, instead of one supervisor juggling growing tool lists. I split the four analytics domains into dedicated Genie-backed subagents (customer analytics, distribution channels, policy & underwriting, claims analytics), each wired to its own Genie Space and its own gold/silver tables, plus a memory-manager subagent handling long-term, cross-conversation memory in a categorized Delta table (preference / fact / decision / project / feedback) that the orchestrator was required to check and update on every turn.

I also designed around real platform constraints rather than fighting them — Agent Bricks' Multi-Agent Supervisor wasn't GA in AIA's Azure region (SEA/East Asia) at the time, so I built the Supervisor logic myself in LangGraph on GA primitives (Agent Framework, Model Serving, Genie, Vector Search, Metric Views, MLflow Tracing) instead of depending on a Beta regional feature.

  • ~35% YTD growth in platform consumption following the engagement start.

  • Two real architectural pivots (single-agent → Supervisor → Deep Agent/Synaptic Command) became a reusable pattern I've carried into every agentic engagement since: specialize early, keep each agent's context and toolset small, and don't depend on Beta/regional features for your core path.

Likely follow-ups — have these ready

  • "Walk me through why the single-agent approach failed." — Name the mechanism: prompt + 20+ tool schemas in context degraded the model's tool-selection accuracy and blew out its effective context window — not just "it got confused."
  • "How does the Supervisor decide which agent to call?" — Intent classification with a confidence score; below 60% it triggers a clarification turn instead of guessing (e.g. "Show me the numbers" → "Which numbers — claims, policies, agents, or customers?").
  • "What stopped two worker agents from seeing different data for the same question?" — The Context Index resolution happens once, centrally, at the Supervisor; results are shared via shared graph state so every worker sees the same resolved assets.
  • "Why move to the Deep Agent pattern if the Supervisor was already working?" — As domains grew, the Supervisor's own tool list started re-approaching the original bloat problem; splitting into self-contained subagents (each with its own context window) removed that ceiling.
  • "How did you validate accuracy?" — MLflow Agent Evaluation against a held-out eval dataset, plus per-node tracing so a wrong answer could be traced back to the exact node/tool call that produced it.
  • "What was the regional constraint, and how did it change your design?" — Agent Bricks' Multi-Agent Supervisor wasn't GA in AIA's Azure region, so the Supervisor was hand-built in LangGraph on GA primitives rather than depending on a Beta feature for the core path.
  • "How do you know the 35% growth was caused by this, not something else?" — Be honest about attribution: it's YTD consumption growth correlated with rollout, a strong signal rather than a controlled experiment — say that plainly if pressed.

SSituation

RapidLR PL is Bajaj Finserv's data pipeline that routes leads through business rules to downstream systems — SFDC CRM and their outbound Dialer. When something went wrong — a lead not reaching SFDC, a feed silently excluded, a master table out of sync — an IT engineer had to manually chase it: pull the right log table by log ID, check exclusion reasons and control flags (sendToSfdc, sfdcFlag), trace whether the issue was upstream ingestion, a stale master table, or a business-rule/filter bug buried in the pipeline's own code, then write it all up in a DevOps ticket. I worked from Bajaj's own historical ticket log — 182 real tickets — to understand the actual shape of the problem before building anything: 58% were master-table maintenance requests (refresh/sync/update), roughly 30% were clarification round-trips, and the rest split across log-lookup investigations, source-system issues, and change requests.

TTask

I owned building an agentic IT support system that could autonomously triage an incoming ticket, investigate it using the same tools a human engineer would, and produce a Root Cause Analysis report — cutting the manual, multi-system chase down to something close to self-service, without giving an LLM free rein over production master tables and pipeline configuration.

AAction

I designed the system around ticket triage first, because the 182-ticket dataset showed the problem wasn't one shape — it was three. I built a classifier that routes each incoming ticket down one of three investigation paths based on trigger signals in the ticket text: a log lookup route (specific log IDs, "data not pushing downstream," exclusion reasons) chaining query_log_view → analyze_exclusion_reason → check_control_flags; a workflow route (pipeline failures, processor errors, feeds stopping entirely) chaining run_pipeline_check → check_upstream_source → query_log_view; and a master maintenance route (table refresh/sync requests — the majority of real volume) chaining update_master_table → refresh_master_table → send_email_notification.

On top of that routing layer I built a LangGraph ReAct agent with 10 domain-specific tools — covering all three routes plus downstream/upstream connectivity checks, control-flag verification, stakeholder email notifications, and direct Azure DevOps ticket updates with the agent's own findings. I grounded the agent with RAG: I built a knowledge base from real historical tickets and their resolution steps, chunked it into Delta tables, and indexed it with Databricks Vector Search using managed embeddings (databricks-gte-large-en), so the agent retrieves similar past tickets and proven resolution patterns before it acts — instead of reasoning from scratch every time.

Where it went further than a support bot: a meaningful share of tickets weren't data problems at all — they were business-rule or filter-logic bugs sitting in the pipeline's own C# source (the Business Rule Engine evaluation step, campaign-routing filters, control-flag misconfigurations). A log-and-master-table agent alone can't find those, so I built a second, dedicated Code Agent with a two-step design rather than handing an LLM the whole repo at once. Step 1 is deterministic, not AI: a CI-triggered indexer pulls the pipeline repo via the GitHub API on every commit and lands it in a Delta table (git_index_raw) tagged by business unit and country/filename, so when a ticket says "Japan data missing from the dashboard, business unit LRS," the agent does a plain filtered lookup — business_unit == 'LRS' AND filename startswith 'japan_' — to fetch the exact file, no guessing. Step 2 hands only that one retrieved file to the LLM (Claude 3.7 Sonnet), prompted as a senior backend engineer, and asks four targeted questions against it: is there filter logic here, a feature-flag restriction, a config exclusion, or a conditional-return block — and to explain plainly what's causing the issue. Keeping the retrieval deterministic and the reasoning step narrow (one file, not a repo-wide search) is what keeps the root-cause explanation grounded instead of the model speculating across code it was never shown. I also indexed the same repo into Vector Search with managed embeddings as a semantic-search path for scaling past exact business-unit/filename matches. That split — an ops agent for data/config issues, a code agent for logic issues — mirrors how I approached the AIA engagement: don't force one agent to be an expert in everything.

RResult
  • Built and shipped a working triage-to-RCA pipeline covering all three investigation routes plus a separate code-level root-cause agent — the two failure modes (data/config vs. business logic) that the historical ticket data showed actually occurred.
  • Grounded every investigation in real precedent: the RAG knowledge base meant the agent wasn't guessing at resolution steps, it was retrieving the same steps a senior engineer had used on a near-identical past ticket.
  • Every automated RCA lands directly in the DevOps ticket with findings attached — engineers review and confirm rather than starting the investigation cold.
On the numbers — say this honestly in the room: I don't have a client-confirmed before/after metric for this one, and I'd tell an interviewer that directly rather than invent one. What I can defend with the data: master-maintenance and straightforward log-lookup tickets together were roughly 70%+ of the historical volume, and both routes are almost entirely mechanical — the kind of ticket where an engineer's real work is "find the right table/log ID, run a known command, confirm, notify" rather than novel judgment. That's exactly the profile where agent automation compresses a multi-system, queue-bound manual investigation (often hours to over a day once you count ticket queue time) down to minutes. If Marcon or anyone pushes for a hard percentage, the honest answer is "I'd estimate 50–60% of ticket volume was a strong fit for full or partial automation based on the ticket mix — I'd want production usage data to confirm the actual resolution-time delta."
Where I'd take it next — graph-based root cause analysis: the current Code Agent's biggest limitation is that it can only see the one file a ticket happens to name. If the real defect sits in a shared function that file calls — a config resolver, a shared validator — the agent never finds it. My next iteration replaces the flat file lookup with a code graph: parse the repo's AST into function/config-key nodes with calls / reads_config edges, then let a LangGraph ReAct agent walk that graph outward from the entry point instead of stopping at hop zero — with tools like get_function, get_callers, and get_config_value. I'd also close the biggest trust gap in the current design: nothing today verifies the LLM's claimed root cause against a real failing record, so I'd add a final step that re-checks the claim against an actual query_log_view result before the RCA goes out. Same principle as the AIA pivot — give the model a way to navigate structure instead of a way to guess across it.

Likely follow-ups — have these ready

  • "What stopped the agent from making a bad change to a production master table?" — Talk about tool scoping: each tool does one narrow, named operation (refresh vs. update vs. sync a specific table) rather than open-ended write access, and every action lands in a reviewable DevOps ticket rather than executing silently.
  • "Why build a separate Code Agent instead of one bigger agent?" — Same lesson as AIA: data/config investigation and source-code logic investigation need different tools and different context — a table-refresh tool and a code-reading tool don't belong in one prompt.
  • "How does the Code Agent avoid hallucinating a root cause?" — By design, it never free-searches the repo. Step 1 is a deterministic Delta filter (business unit + filename/country) that retrieves exactly one file; step 2 hands only that file to the LLM with four targeted questions (filter logic, feature flag, config exclusion, conditional return). The model reasons over real code it was actually shown, not a repo-wide guess.
  • "How does the code index stay current?" — It's designed to sync on commit — a CI/GitHub Action trigger re-indexes changed files into the Delta table, so the agent isn't working off a stale snapshot of the pipeline.
  • "How did you decide which route to send a ticket down?" — Trigger signals in the ticket text itself — specific log IDs and "not pushing downstream" language route to log lookup; pipeline/processor failure language routes to workflow; refresh/sync language routes to master maintenance.
  • "What would you need to actually prove the time savings?" — Be ready to say it plainly: production rollout with before/after resolution-time tracking per ticket_type — you'd want that instrumented from day one next time, not retrofitted.
  • "How would you improve this if you rebuilt it today?" — Lead with the graph-based redesign: a code knowledge graph (AST-parsed functions/config keys as nodes, calls/reads as edges) walked by a LangGraph ReAct agent, plus a verification step against real log data — see the full writeup linked below.
