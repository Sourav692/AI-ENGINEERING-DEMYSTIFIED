SSituation

DevRev's own system design prep guide names Problem Type A as "design an AI agent platform for non-technical users to configure workflow automations across multiple channels" — email, chat, Slack, web forms, webhooks. The hard part isn't running an agent; it's letting someone non-technical wire one up safely. Most answers to that prompt stay at the slide level — "we'd add guardrails," "we'd make it idempotent" — without ever having to defend those claims against a system that can actually be attacked.

TTask

I set out to turn three specific claims from that prep guide into checkable properties of a real, runnable system rather than bullet points: (1) a destructive action never executes without an explicit human approval or an explicit per-tenant allow-list entry, even on a fully autonomous workflow; (2) a retried or redelivered action never applies its side effect twice; (3) a crash mid-run never re-runs a step that already completed. I scoped it deliberately narrow — no LLM, no real connectors — so every property could be proven with a fast, deterministic test instead of an LLM's mood on the day.

AAction

I designed the system so that every automated action has to earn its right to run on its own — nothing executes just because it technically could. Anything destructive, like issuing a refund, either needs a human to click approve first, or has to be on a pre-approved list for that specific customer. Nothing in between.

To prove a retry never charges someone twice, I gave every individual action its own one-time "receipt" the moment it runs. If the same action gets asked for again — because a network hiccuped and the request came through twice — the system recognizes the receipt already exists and simply does nothing the second time, instead of repeating the action.

To prove a crash never loses or repeats work, I built the system so it always remembers exactly which step it was on. I tested this literally — I killed the process mid-run on purpose, restarted it, and watched it pick up exactly where it left off, never redoing a step that had already happened.

A design decision I'm proud of: I kept two safety checks separate on purpose instead of merging them into one. One check asks "which automation is the right one to respond to this event?" — a business decision. The other asks "is anything else already touching this same customer record right now?" — a safety rule that has to hold no matter what. Same logic for spending limits: "has this run taken too many steps overall?" is a different question from "is this one action about to spend too much money?" A $500 refund against a $50 limit gets stopped immediately, on dollars alone — it can't sneak through by looking cheap on step count.

Finally, I built a five-stage rollout path — draft, test on sample data, watch real traffic without touching it, go live with human approval on every risky action, then finally fully autonomous — and made sure only a second person, never the person who built the automation, can move it forward a stage. Same idea as requiring a second reviewer before code ships, applied to automation instead.

RResult
  • Reproduced DevRev's own "Cascade Robotics" $500-refund scenario end to end and showed exactly why it did not fire automatically: not budget (a $500 refund against a $50 cap is refused outright, never silently clamped down), but that issue_refund wasn't allow-listed for autonomous use on that tenant — so the run correctly paused for a human.
  • Proved idempotency directly: retried issue_refund against an existing idempotency key and confirmed exactly one apply, not two.
  • Proved durability directly: crashed a run after step 0, resumed it, and confirmed step 0 never re-ran — the resume path is the same loop, not a different one.
  • Built a negative-control demo exercising seven distinct denial paths (wrong role trying to self-promote, skipping a rollout stage, a type mismatch, a not-yet-LIVE workflow, the spend cap, the step budget, a locked entity) — all correctly denied, all logged with a named reason, never a silent stop.
  • Named the scope honestly rather than overselling it: locks and idempotency-key storage are in-process Python dicts, correct in shape but not surviving a restart or shared across workers — documented directly in the coverage map instead of hidden.

Likely follow-ups — have these ready

  • "Why no LLM at all?" — The reasoning-loop shape (plan → select → call → observe → iterate, hard step cap) is real; swapping the fixed step sequence for an LLM planner is a bounded, named extension, not a redesign — and keeping it deterministic meant every guardrail property could be proven with a fast, exactly-reproducible test instead of fighting model non-determinism.
  • "How would this survive a process restart in production?" — Name it directly: locks and the idempotency-key store move from in-process dicts to something like Redis/Postgres with the same key shape ({run_id}:{step_name}) — the logic doesn't change, only where it's persisted.
  • "Why two separate checks for routing and two for limits instead of one each?" — Walk through the concrete failure each collapse would cause: a misconfigured priority becoming a correctness bug; a workflow "spending down" its step budget to dodge the dollar cap.
  • "What stops the workflow's own author from promoting it straight to AUTONOMOUS?" — Promotion is gated to the approver/admin roles at the identity layer, checked at every stage transition, not just enforced by UI affordance.

60-second spoken version

"DevRev's prep guide names 'agent platform for non-technical users' as a design problem, and the easy trap is answering it with slide bullets — 'we'd add guardrails, we'd make it idempotent.' I built a real, runnable version instead, scoped deliberately without an LLM so every property could be proven with a fast, deterministic test. I proved three things directly: a destructive action never runs without approval or an allow-list entry — I reproduced DevRev's own $500-refund scenario and showed it's not a budget problem, it's that the action wasn't allow-listed for autonomous use, so it correctly paused for a human. A retry never double-applies — I retried a refund against an existing idempotency key and got exactly one apply. And a crash never re-runs a completed step — I actually crashed a run mid-flight and resumed it. The design choice I'm proudest of is keeping routing priority and the entity lock as two independent checks, and the step budget and spend cap as two independent checks, because collapsing either pair turns a misconfiguration into a correctness bug instead of a config mistake."

SSituation

The thing that actually makes enterprise RAG hard isn't retrieval quality — it's that not everyone is allowed to read everything, so the same question has different correct answers for different people. I framed it as a concrete B2B SaaS scenario: "Why did Vertex Financial lose data in March, and do they get service credits?" A Tier-1 support agent should get the platform-side backlog; a Tier-3 engineer should get the engineering root cause; an account manager should get the contractual credit tiers but not the root cause; an external contractor and anyone outside the tenant should get nothing. Getting that right provably, not by prompting the model nicely, was the whole point.

TTask

I owned building an enterprise RAG platform end to end where policy correctness was a gated, tested property of the system — not a hope resting on the LLM refusing nicely — while still being honest about what a small, near-perfect eval corpus can and can't prove.

AAction

I built the system so that permission-checking always happens before the AI ever sees a single document — not as a coding convention someone could forget, but wired directly into the shape of the pipeline itself, so it's structurally impossible to skip. I split access control into two layers on purpose. The first is a fast, cheap filter that narrows the search down to only documents this person could plausibly see — like a bouncer doing a quick ID check at the door. The second is a slower, thorough re-check right before the answer is written, using the person's up-to-the-second permissions — embargoes, group membership, whether access was just revoked — because the fast filter can go stale between when it was built and the moment someone asks a question. If that second check ever catches something the first one should have caught, that's flagged as a security incident, not quietly ignored, because it means the fast filter has drifted out of date. On top of both, I physically separated every customer's data into its own storage bucket, so even a bug in the permission logic can't leak one customer's data into another's answer. The permission rules themselves are seven plain-language checks — which company you belong to, your clearance level, your region, timing windows, whether you need-to-know this topic, whether you're an external contractor, and "deny by default" if nothing explicitly allows it.

I also tried six different ways of searching the documents — from simple keyword and similarity search up to a more elaborate approach that breaks a complex question into sub-questions and re-ranks the results — and measured all of them against the same test set, so the choice of search method was based on evidence, not a guess.

Three real mistakes my own testing caught before they became real problems: First, a false alarm — the system flagged itself for "leaking" a document to an account manager, but she was actually allowed to read it; I'd mislabeled "not relevant to this question" as "not allowed to see it" in my own test data. I fixed the test data and added a check that keeps those two ideas from ever being confused again — a false security alarm is worse than no alarm, because people learn to ignore it. Second, I found a rule that was never actually being tested — one permission check kept getting shadowed by an earlier, stricter check firing first, so I added a specific test person whose only path to being blocked was that exact rule, to confirm it worked on its own. Third, I found one test that passed or failed almost at random, because I'd made the AI's own judgment part of the pass/fail decision. I fixed that by separating "did we leak data" — decided by hard rules, never by the AI — from "did we phrase the refusal well" — which can be a judgment call. Security can never come down to a coin flip.
Rebuilding it on a second platform (Databricks) surfaced a real gap, not just a copy-paste port: that platform's own search index doesn't automatically inherit the company's central permission rules — it's a separate copy of the data, so a permission change doesn't travel with it on its own. I designed around that the same way — fast filter for speed, then a second, authoritative check against the real, live-governed source before answering. Being able to show both versions, and explain exactly why that second check is non-negotiable on that platform, was the whole point of building it twice.

RResult
  • 22/22 golden-set pass on the production ("enterprise") strategy: recall@k 1.00, MRR 1.00, groundedness 1.00, refusal accuracy 100%, 0 leaks (the hard release gate), 0 distractions, p50 10.7s, $0.0196/query.
  • Ran the full six-strategy comparison on the same golden set — every strategy scored 0 leaks; dense was the cheapest/fastest at this corpus size, HyDE had the best MRR (1.00) at the cost of lower groundedness (0.929), enterprise was the most expensive and slowest by design, trading cost for the decomposition + reranking that a larger corpus would need.
  • 68 tests passing (62 fast — policy, fusion, chunking, enforcement, golden-set integrity — plus 6 live integration tests against OpenAI), plus a standalone script asserting the security-reference doc matches the running policy so documentation can't silently drift from code.
  • Shipped a second, Databricks-native version of the same system proving the same properties on Unity Catalog + Vector Search + MLflow, specifically to demonstrate the extra enforcement layer that platform requires and a ChromaDB-only design would miss.
Read these numbers honestly — say this in the room: The corpus is 22 documents. Retrieval is easy at that size, so every strategy scores near-perfectly on quality and the differences between them are mostly noise — this table is not proof that HyDE or multi-query earn their keep; "enterprise" is simply the slowest and priciest here, and dense would be the right production choice for a corpus this small. The value is that the harness exists and gates the release at all — on a 200,000-document corpus, the same table is what tells you whether HyDE's extra latency is actually earning its keep. The number that matters at any corpus size is the zero-leak column.

Likely follow-ups — have these ready

  • "Why two enforcement layers instead of just filtering the vector search well?" — The pre-filter is an optimization on attributes that were true when the index was built; it can go stale (a revoked group, an expired embargo) without a reindex. The post-check re-evaluates on fresh attributes right before generation, so staleness in the index can never become a leak — it becomes a logged security event instead.
  • "How do you know the eval isn't just testing itself?" — Point to the three caught bugs directly: the false alarm, the shadowed rule, and the flaky gate were all found by the harness disagreeing with itself or with a hand-labeled case, and each fix has a test that prevents the same drift from recurring.
  • "What breaks first at 200k documents instead of 22?" — Retrieval quality differentiation reappears (this is where HyDE/multi-query would actually need to justify their latency), and Chroma's per-tenant-collection isolation approach needs revisiting for collection-count scaling — both are named explicitly in docs/Scale_Optimization.md rather than glossed over.
  • "Why does Databricks need a second enforcement layer if Unity Catalog already governs the data?" — Because Vector Search indexes are a derived copy of the data; UC's row filters and column masks apply to the governed table, not automatically to a copy of its embeddings sitting in a separate index.

60-second spoken version

"I built an enterprise RAG platform around the part that actually makes enterprise RAG hard — not everyone's allowed to read everything, so the same question needs a different correct answer per person. I split access control into two layers: a cheap pre-filter compiled into the vector search for speed, and an authoritative post-check on fresh attributes right before generation for correctness, plus physical per-tenant isolation so a filter bug can't cross a tenant boundary. I built a golden-set eval harness that gates releases on a hard zero-leak number, and it actually caught three real bugs during development — a false security alarm from conflating 'unauthorised' with 'irrelevant,' a policy rule that no test case was actually exercising, and a flaky LLM-judged gate that I moved off the security-critical path entirely, because security can't hinge on a coin flip. Final numbers: 22 of 22 on the golden set, zero leaks, 68 tests passing. Then I rebuilt the same system on Databricks and found a real platform gap — Vector Search doesn't enforce Unity Catalog's row filters — which is exactly why that second enforcement layer isn't optional, it's the whole design."
